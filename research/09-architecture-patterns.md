# 09. Архитектурные паттерны

> Связь со SPEC: разделы 5 (агенты), 6 (консенсус), 7 (БД), 10 (структура кода).

## Вопрос

Как устроены подобные LLM-пайплайны? Нужен ли агентный фреймворк, и какие технические приёмы (структурированный вывод, кэш, батчи, наблюдаемость) обязательны?

## Короткий ответ

- Наш пайплайн по классификации Anthropic — это **workflow, а не агент**: цепочка промптов (Методист → Генератор), параллельный запуск с голосованием (Аналитик + Скептик) и цикл «генератор-оценщик» (ретрай с причиной отказа). Для таких схем рекомендуют **простой код без фреймворков** — как и записано в SPEC 10.
- Обязательные приёмы: **structured outputs**, **кэширование** стабильного префикса, **Batch API** для неинтерактивных прогонов, **версии промптов** в журнале, фиксированный **набор для оценки**.

## Что известно

### Паттерны Anthropic (*Building effective agents*, 2024)

| Паттерн | Суть | У нас |
|---|---|---|
| Prompt chaining | Последовательные шаги, каждый обрабатывает выход предыдущего | Методист → Генератор |
| Routing | Классификация входа и маршрутизация | Банк задач или генерация (5.5) |
| Parallelization | Параллельные подзадачи или голосование | Аналитик + Скептик |
| Orchestrator-workers | Центральная LLM динамически раздаёт задачи | Не нужно |
| Evaluator-optimizer | Одна LLM генерирует, другая оценивает, цикл | Ретрай с причиной отказа, `generator_answer_error` |

- Про фреймворки: начинать с прямых вызовов API — «многие паттерны реализуются в несколько строк кода». Фреймворки прячут промпты и ответы и усложняют отладку.
- Агенты нужны для открытых задач, где число шагов нельзя предсказать. Наш процесс предсказуем, это workflow.
- Evaluator-optimizer работает, когда есть **ясные критерии оценки** и доработка по отзыву даёт измеримую пользу. У нас критерии есть (SPEC 6).

### Технические приёмы (документация Claude API)

- **Structured outputs:** `output_config.format` с JSON-схемой гарантирует формат ответа; для инструментов — `strict: true`.
- **Prompt caching:** кэшируется префикс (инструменты → system → сообщения). Любое изменение в префиксе ломает кэш, поэтому нельзя вставлять в системный промпт время или id запроса. Проверять по `usage.cache_read_input_tokens`.
- **Batch API:** −50%, результаты приходят в любом порядке — сопоставлять по `custom_id`.
- **Параллельные запросы с одинаковым префиксом не читают кэш друг друга**: кэш доступен только после начала ответа первого запроса. Аналитик и Скептик у нас разные модели или промпты, так что общего кэша у них и нет.
- **Серверное исполнение кода** — готовая песочница для программной проверки (см. [05](05-verification.md)).

## Как решали другие

- Датасеты вроде FLAMES и OpenMathInstruct-2 устроены как **конвейеры из простых шагов**: генерация → фильтр решаемости → решение → проверка → очистка. Каждый шаг логируется отдельно, чтобы понимать, где теряется качество.
- **Разработка через оценку (eval-driven):** фиксированный набор входов, на котором сравниваются версии промптов и моделей.

## Проблемы и ограничения

- **Метрики смешаются, если промпты меняются без учёта.** В SPEC у `attempts` нет версии промпта, так что после правки промпта Генератора старые и новые попытки будут в одной куче.
- **Нестабильность.** Даже без `temperature` одинаковый вход даёт разные задачи — сравнивать версии нужно на достаточном числе прогонов.

## Выводы для прототипа

1. **Оставить простой код без фреймворков** (подтверждает SPEC 10).
2. **Structured outputs для всех агентов**, JSON-схемы хранить рядом с промптами.
3. **Добавить `prompt_version`** (например, хэш файла промпта) и `model` в `attempts` — без этого нельзя сравнивать итерации.
4. **Фиксированный набор для оценки:** 5 профилей × N ТЗ, на которых прогоняется каждая новая версия промптов. Результаты сравниваются по метрикам SPEC 9.
5. **Кэш** на системный промпт и few-shot Генератора; **Batch API** для прогонов ради датасета.
6. **Песочница для кода-решателя:** серверное исполнение кода Anthropic или локальный Docker без сети.

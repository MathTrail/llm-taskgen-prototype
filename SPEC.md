# llm-taskgen-prototype — что я хочу проверить

> Рабочий черновик. Места с пометкой **[решить]** — открытые, их надо поправить или вычеркнуть.

## 1. Зачем этот прототип

**Гипотеза:** цепочка LLM-агентов по профилю ученика может сама решить, какую задачу ему дать дальше, и сгенерировать решаемую, однозначную олимпиадную задачу в стиле «Кенгуру» для 1–4 классов.

**Язык:** задачи, промпты агентов и все данные только на английском. Сам этот документ остаётся на русском.

**Формат:** только текстовые задачи, без рисунков.

Что конкретно проверяю:

1. **Выбор задачи.** Методист по «сырому» профилю (история решений, ошибки, интересы) осмысленно выбирает тему, сложность и цель следующей задачи.
2. **Генерация.** Генератор по этому ТЗ делает задачу, похожую на «Кенгуру»: короткий сюжет, нестандартная идея, 5 вариантов ответа с продуманными ловушками.
3. **Верификация.** Два независимых верификатора отсеивают нерешаемые и неоднозначные задачи.
4. **Цена.** Сколько стоит и сколько длится получение одной хорошей задачи (токены, время, число попыток).

**Побочный продукт:** два датасета для будущего дообучения локальных моделей: «ТЗ → задача» (для генератора, приоритетный) и «условие → пошаговое решение» (для решателя).

Код одноразовый. После проверки гипотезы он выбрасывается, в основную систему переносятся промпты, схемы данных и выводы.

## 2. Что НЕ входит в прототип

- k8s, Kafka, Go, воркеры, очереди.
- pgvector: всё хранится в PostgreSQL (раздел 7), но поиск по смыслу не используем.
- UI: только консоль.
- Fine-tuning: только собираем для него данные.
- Реальные ученики: профили выдуманные.
- Задачи с рисунками: в прототипе только текстовые задачи.
- Способ, которым ученик даёт обратную связь (кнопка «не понимаю», видео, голос, текст). В прототипе это просто поле `feedback` в истории профиля.

## 3. Как это выглядит при запуске

```bash
docker compose up -d      # PostgreSQL (раздел 7)
python seed.py            # один раз: загрузить стартовые профили из db/seed/*.json
python main.py --student masha
```

1. Скрипт читает профиль ученика из БД.
2. **Методист** выдаёт ТЗ на задачу, оно печатается в консоль.
3. **Поиск в банке задач** (см. 5.5). Нашлась подходящая задача, которую ученик ещё не получал, — выдаём её, генерацию пропускаем.
4. Не нашлась — **Генератор → Аналитик + Скептик**, до 3 попыток. Принятая задача записывается в банк.
5. Выданная задача записывается в `student_tasks` этого ученика.
6. В консоли итоговая задача, варианты, правильный ответ, решение Аналитика и сводка: откуда задача (банк или генерация), сколько было попыток, токенов, денег, секунд.
7. Запрос и все попытки пишутся в БД (раздел 7).

Флаг `--fresh` отключает поиск в банке: задача всегда генерируется. Без него банк быстро начнёт отдавать готовые задачи, и Генератор с верификаторами почти перестанут проверяться, поэтому для экспериментов и сбора датасетов нужен этот режим.

### Режим `--answer` (симуляция ученика)

```bash
python main.py --student masha --answer
```

Цикл работает прямо с БД:

1. Скрипт загружает профиль ученика из `students` и последние 5 записей его истории из `student_tasks`.
2. Методист → поиск в банке → (если не нашлась) Генератор → Аналитик + Скептик. Задача выводится в консоль и записывается в `student_tasks`.
3. Скрипт ждёт ввод: `A`–`E`, `?` («не понимаю»), `H` (подсказка) или `exit`. На `H` показывается `hint` Генератора, и скрипт снова ждёт ответ.
4. Скрипт сам сравнивает ответ с `correct_answer` и показывает разбор:
   - неверный ответ → сначала текст ловушки `distractors[выбранная буква]`, потом полное решение Аналитика (`solving_thought_process`);
   - верный ответ или `?` → полное решение Аналитика.
5. Ответ сохраняется в строку `student_tasks` этой задачи:
   - верный ответ → `correct: true`;
   - неверный → `correct: false`, `chosen_option` и `trap_hit` = `distractors[выбранная буква]`;
   - `?` → `correct: null`, `feedback: "didn't understand the question"`;
   - `hint_used: true`, если ученик брал подсказку;
   - `pace` — по времени от показа задачи до ответа, с простыми порогами из `config.yaml`.
6. `consecutive_failures` в `students` обнуляется после верного ответа и растёт на 1 после неверного или `?`. Подсказка неудачей не считается.
7. Методисту передаются последние 5 записей истории, а в БД хранится вся.
8. Следующая итерация начинается с Методиста на уже обновлённом профиле.

В цикле меняются только история ответов и `consecutive_failures`. `cognitive_profile` и `mastered_topics` не меняются.

Если задача не прошла за 3 попытки, скрипт сообщает «задача не получилась» и начинает новую итерацию с Методиста, передав ему неудавшееся ТЗ, чтобы он не выбрал то же самое. В одиночном запуске скрипт в этом случае завершается с ошибкой.

Всё пишется в БД сразу, поэтому следующий запуск продолжает с того места, где остановился прошлый, и ученик не получит повторно ту же задачу. Чтобы начать эксперимент заново, ученика сбрасывают в стартовый профиль командой `python seed.py`.

**Зачем:** без этого режима Методиста можно проверить только на статичных профилях. С ним видно, как он меняет цель после ошибок (`new_topic` → `reinforce` → `motivate`) и как свежий `trap_hit` отражается в следующем ТЗ. Заодно проверяется разметка ловушек: намеренно выбираю неверный вариант и смотрю, какая причина ошибки попала в историю.

## 4. Входные данные

### 4.1 Профиль ученика

Профиль хранится в БД, в таблицах `students` и `student_tasks` (раздел 7). Стартовые профили я пишу руками в JSON в формате ниже (`db/seed/*.json`) и загружаю в БД командой `python seed.py`. `history` при загрузке превращается в строки `student_tasks`.

Состав профиля — гипотеза. Какие поля реально важны, покажет прототип (см. `profile_fields_used` в 5.1).

```json
{
  "id": "masha",
  "grade": 3,
  "interests": ["space", "robots"],
  "cognitive_profile": [
    "doesn't read long questions to the end and loses interest",
    "off-by-one when counting gaps",
    "misses the word \"not\" in the question"
  ],
  "mastered_topics": ["logic.knights_liars"],
  "excluded_skills": ["division_with_remainder", "fractions"],
  "consecutive_failures": 2,
  "history": [
    {
      "task_id": "t-0012",
      "topic": "logic.knights_liars",
      "difficulty": 3,
      "correct": true,
      "pace": "fast"
    },
    {
      "task_id": "t-0013",
      "topic": "combinatorics.enumeration",
      "difficulty": 4,
      "correct": false,
      "chosen_option": "B",
      "trap_hit": "missed one case while enumerating",
      "hint_used": true,
      "pace": "struggled"
    },
    {
      "task_id": "t-0014",
      "topic": "time.clocks",
      "difficulty": 3,
      "correct": null,
      "feedback": "didn't understand the question",
      "pace": "struggled"
    }
  ]
}
```

| Поле | Что это | В прототипе | В целевой системе |
|---|---|---|---|
| `grade` | Класс ученика | вручную | из профиля |
| `interests` | Интересы, из них Методист берёт сеттинг | вручную | из профиля |
| `cognitive_profile` | Устойчивые особенности и типичные ошибки ученика, одним списком | вручную | обновляется автоматически по `trap_hit` (фоновый процесс или Методист в конце сессии) |
| `mastered_topics` | id тем из `topics.json`, которые ученик уже закрыл. Нужны, чтобы при `new_topic` не ходить по кругу | вручную | бэкенд по истории |
| `excluded_skills` | id навыков из `skills.json` (см. 4.4), которых ученик ещё не проходил в школе. Нельзя использовать ни в условии, ни в ловушках | вручную | вручную или по школьной программе класса |
| `consecutive_failures` | Сколько задач подряд не решено (неверный ответ или «не понял»). Помогает Методисту вовремя выбрать `motivate` | вручную | бэкенд |
| `history` | 3–5 последних задач | вручную | 3–5 последних задач плюс сводка успеваемости вместо полной истории |
| `history[].pace` | Темп: `fast`, `normal` или `struggled`. Секунды LLM не с чем сравнить, поэтому передаём готовый тег | вручную | бэкенд по времени решения и норме для класса |
| `history[].trap_hit` | Какую ловушку поймал ученик (см. ниже) | вручную | по разметке `distractors` Генератора |
| `history[].feedback` | Обратная связь ученика по задаче, например «не понимаю» | вручную | канал обратной связи (см. раздел 11) |
| `history[].hint_used` | Брал ли ученик подсказку | вручную | по действиям ученика |

Колонка «В прототипе» относится к стартовому профилю. В режиме `--answer` новые записи истории и `consecutive_failures` пишет сам скрипт.

Как хранятся поля:

- `grade`, `consecutive_failures`, `mastered_topics`, `excluded_skills`, `interests` — обычные колонки и массивы, только точное сравнение. Векторы здесь вредны: поиск по смыслу может счесть запрещённый навык «похожим» на разрешённый.
- `cognitive_profile` — в прототипе массив строк, Методист получает его целиком. Когда записей станут сотни, понадобится семантическая память (см. раздел 11).

- `trap_hit` берётся из разметки ловушек Генератора (см. 5.2). Если ученик выбрал B, а Генератор пометил B как «missed one case while enumerating», значит, мы знаем, какую именно ошибку он сделал. Эта связка, по-моему, самое ценное в профиле.
- Правил по классам (вроде «для 1 класса условие короче») нет. Методист подстраивает длину и сложность формулировки под конкретного ученика по его истории, `cognitive_profile` и `feedback` и передаёт это Генератору в `constraints`.

### 4.2 Каталог тем

`topics.json` — плоский список тем 1–4 классов с id и коротким описанием. Методист выбирает тему **из каталога**, а не придумывает её сам, иначе историю разных учеников и запусков нельзя будет сравнить.

Главный фильтр — только текстовые задачи. Тема должна однозначно формулироваться словами, без рисунка и без пространственного воображения: с дискретной логикой и перебором модели справляются хорошо, а геометрию «в уме» представляют ненадёжно.

**Берём:**

| id | Тема | Примеры |
|---|---|---|
| `logic.ordering` | Упорядочивание | кто за кем стоит, кто старше или выше |
| `logic.knights_liars` | Рыцари и лжецы, истинные и ложные утверждения | |
| `combinatorics.enumeration` | Перебор вариантов | рукопожатия, простые маршруты, описанные словами, числа из заданных цифр |
| `counting.gaps` | Промежутки и границы (ловушка ±1) | распилы брёвен, деревья в ряд, этажи |
| `time.clocks` | Часы | разница во времени |
| `time.calendar` | Календарь и возраст | сдвиг дней недели, возраст через несколько лет |
| `pigeonhole.basic` | Простейший принцип Дирихле | сколько носков вытащить в темноте, чтобы точно была пара |
| `parity.alternation` | Чётность и чередование | свойства чисел, чередование в последовательности |
| `arithmetic.tricks` | Арифметика с хитростью | удобный порядок действий, «задумал число» |
| `algorithms.weighing_pouring` | Взвешивания и переливания | |
| `patterns.sequences` | Закономерности в последовательностях | |

**Исключаем:**

- **Пространственная геометрия:** развёртки кубиков, перекатывание кубика, оригами (складывание и разрезание бумаги). Без рисунка условие выходит либо неоднозначным, либо длинным и сухим, не в стиле «Кенгуру».
- **Визуальный подсчёт:** «сколько треугольников на картинке», наложение фигур.
- **Симметрия и зеркальные отражения:** верификаторы по-разному поймут оси симметрии в текстовом описании, консенсуса не будет.
- **Геометрия, описанная словами:** периметр, клетчатые фигуры. Та же проблема, что с пространственной геометрией.
- **Тяжёлая арифметика и дроби:** не формат «Кенгуру» для 1–4 классов и провоцирует вычислительные ошибки модели.
- **Школьные задачи на движение и работу:** встречные поезда, трубы и бассейн. Это школьная рутина, а не олимпиадная логика.

### 4.3 Эталонные задачи (few-shot)

`examples/kangaroo.json` — по 3 задачи «Кенгуру» на каждую тему каталога (~33) из англоязычных выпусков (Math Kangaroo), подбираю вручную. У каждой размечены тема, класс, баллы, правильный ответ и короткое решение. Генератору подаём 3 примера по теме ТЗ, в первую очередь того же уровня класса (1–2 или 3–4). Отбираем простым фильтром, без векторного поиска. Векторный поиск по задачникам и потом пригодится только как источник примеров: научить модель рассуждать он не может, для этого нужно дообучение.

Реальные задачи «Кенгуру» используем только в промптах как образец стиля, в датасеты их не кладём.

**Шкала сложности.** В «Кенгуру» задачи стоят 3, 4 или 5 баллов. Берём эти баллы как готовую шкалу сложности (`difficulty`). Баллы считаются внутри уровня класса: задача на 3 балла для 1 класса и для 4 класса — разные задачи.

### 4.4 Каталог навыков

`skills.json` — закрытый список школьных навыков с id и коротким описанием: `multiplication`, `division_with_remainder`, `fractions` и т. д. `excluded_skills` в профиле и в ТЗ ссылается только на id из этого каталога, как `mastered_topics` — на `topics.json`. Иначе точное сравнение в банке задач (5.5) не сработает: «fractions» и «simple fractions» для него разные навыки.

## 5. Агенты

```
  [Профиль ученика] + [Каталог тем]
            │
            ▼
     ┌─────────────┐
     │  Методист   │ → ТЗ: тема, сложность, цель, сеттинг, ловушки
     └─────────────┘
            │
            ▼
   Банк задач (PostgreSQL): есть подходящая,
   и ученик её не получал?
     ├─ да  → выдаём её, генерацию пропускаем
     └─ нет
            │
            ▼
     ┌─────────────┐ ◄── 3 эталонные задачи
     │  Генератор  │ → условие, варианты A–E, задуманный ответ X, решение
     └─────────────┘
            │   (дальше уходят только условие и варианты)
     ┌──────┴───────────┐
     ▼                  ▼
┌───────────┐     ┌───────────┐
│ Аналитик  │     │  Скептик  │  (другая модель, не как у Генератора)
│ ответ Y   │     │ ответ Z   │
│           │     │ + issues  │
└───────────┘     └───────────┘
     └──────┬───────────┘
            ▼
   X == Y == Z и нет блокирующих issues?
     ├─ да  → выдаём задачу + пишем в банк и датасеты
     └─ нет → новая попытка Генератора (до 3) с причиной отказа
```

### 5.1 Методист (Tutor)

**Роль:** решает, *что* дать ученику прямо сейчас.
**Вход:** профиль, каталог тем.
**Выход:**

```json
{
  "rationale": "Two failures in a row: missed a case in enumeration, then didn't understand a clocks question. Give an easier, short enumeration task to rebuild confidence.",
  "pedagogical_goal": "motivate",
  "target_concept": "combinatorics.enumeration",
  "difficulty": 3,
  "setting": "space",
  "traps_to_use": ["missed one case while enumerating", "double counting"],
  "constraints": ["question no longer than 3 sentences"],
  "excluded_skills": ["division_with_remainder", "fractions"],
  "profile_fields_used": ["consecutive_failures", "history", "cognitive_profile"]
}
```

`pedagogical_goal` принимает одно из трёх значений: `reinforce` (закрепить слабое место), `motivate` (дать задачу полегче для уверенности) или `new_topic` (перейти к новой теме).

`excluded_skills` Методист переносит из профиля в ТЗ, чтобы Генератор не использовал эти навыки ни в условии, ни в ловушках. Генератор получает описания этих навыков из `skills.json`.

`profile_fields_used` — поля профиля, на которые Методист опирался при выборе. По ним видно, какие поля профиля реально работают, а какие лишние (см. раздел 9).

### 5.2 Генератор

**Роль:** придумывает задачу по ТЗ.
**Вход:** ТЗ от Методиста; 3 эталонные задачи по теме; последние задачи ученика, чтобы не повторяться (модель склонна повторять одни и те же сюжеты, это отдельно проверяет метрика «Разнообразие»); на повторной попытке — причина, по которой отклонили прошлую.
**Выход:**

```json
{
  "design_thought_process": "Plot: spaceships docking. Count the pairs, the answer is 6. Trap 5: one pair missed. Trap 12: every pair counted twice.",
  "question": "…",
  "options": {"A": "4", "B": "5", "C": "6", "D": "8", "E": "12"},
  "correct_answer": "C",
  "solution": "…",
  "hint": "How many ships can the first ship dock with?",
  "distractors": {
    "A": "…",
    "B": "missed one pair while enumerating",
    "D": "…",
    "E": "every pair counted twice"
  }
}
```

- `hint` — один наводящий вопрос или первый шаг к решению. Ответ не раскрывает. Ученик видит его до ответа, если попросит.
- `distractors` нужен, чтобы по неверному ответу ученика понять его ошибку (поле `trap_hit` в профиле). Этот же текст ученик видит после неверного ответа.
- Отдельного агента для подсказок и разбора нет. Всё готовится заранее в этом JSON, чтобы не тратить лишний вызов (3–5 секунд и токены) на каждую подсказку или ошибку.

### 5.3 Аналитик (верификатор 1)

**Роль:** честно решает задачу вслепую.
**Вход:** только `question` и `options`. Задуманный ответ и решение Генератора он не видит.
**Настройки:** минимальная случайность (temperature 0, если модель это позволяет).
**Выход:**

```json
{
  "solving_thought_process": "Step 1: … Step 2: … So there are 6 pairs.",
  "final_answer": "C"
}
```

Аналитик пишет шаги простым языком, как тренер объясняет ученику 1–4 класса. Этот же текст попадает в датасет для обучения решателя и показывается ученику как разбор после ответа. Разбор берём у Аналитика, а не `solution` Генератора, потому что именно этот текст идёт в датасет как эталон.

### 5.4 Скептик (верификатор 2)

**Роль:** ищет, почему задача *плохая*, и только после этого решает её.
**Вход:** те же `question` и `options`.
**Модель:** Claude Sonnet 5 — не та модель, что у Генератора (см. раздел 8).
**Выход:**

```json
{
  "issues": [
    {"type": "ambiguous", "severity": "blocking", "comment": "Unclear whether pairs A–B and B–A count as different."}
  ],
  "option_check": {
    "A": "wrong because …",
    "B": "wrong because …",
    "C": "correct",
    "D": "wrong because …",
    "E": "wrong because …"
  },
  "final_answer": "C"
}
```

- Возможные `type` в `issues`: `ambiguous`, `missing_data`, `multiple_correct`, `no_correct`, `too_hard_for_grade`, `needs_picture`, `factual_error`.
- `severity`: `blocking` (задачу отклоняем) или `minor` (задачу оставляем, замечание сохраняем).
- `option_check` проверяет, что верен ровно один вариант.
- Если решить задачу нельзя, `final_answer` = `"UNSOLVABLE"`.

### 5.5 Банк задач

Все принятые задачи хранятся в таблице `tasks` (схема — в разделе 7). Перед генерацией скрипт ищет в банке готовую задачу под ТЗ Методиста.

**Обязательные условия** (SQL `WHERE`):

- тема и баллы совпадают с ТЗ;
- уровень класса совпадает с классом ученика (1–2 или 3–4);
- `tasks.excluded_skills @> <excluded_skills ученика>`: задача сгенерирована при тех же или более строгих запретах, значит запрещённых для ученика навыков в ней нет;
- задачи нет в `student_tasks` этого ученика: одну задачу ученик никогда не получает дважды, даже если тогда ошибся.

**Выбор лучшей** из подходящих (в коде): сначала совпадение `setting` с ТЗ, потом больше общих ловушек с `traps_to_use`. Не нашлось ни одной — генерируем.

Почему без pgvector: темы в каталоге дискретные, точных условий хватает, а поиск по смыслу может вернуть «похожую» тему вместо нужной. pgvector подключим, когда тексты ТЗ станут слишком разнообразными для точных условий.

Для задачи из банка в `requests` пишется источник `bank`, новых попыток и записей в датасетах не появляется. В историю ученика она попадает как обычно: `trap_hit` берётся из сохранённых `distractors`.

## 6. Консенсус и ретраи

Аналитик и Скептик вызываются параллельно: оба получают только условие и варианты и друг от друга не зависят.

Задача **принимается**, если:

1. JSON всех агентов валиден, вариантов ровно 5 и все они разные, в `distractors` ровно 4 ключа (все варианты, кроме верного), `hint` не пустой;
2. ответ Генератора == ответ Аналитика == ответ Скептика;
3. у Скептика нет issues с `severity: blocking`.

Одного совпадения трёх ответов мало: одинаковые буквы не гарантируют, что условие однозначно, что остальные варианты неверны и что задача подходит по возрасту и интересна. Поэтому у Скептика есть `issues` и `option_check`, а принятые задачи ещё проверяются вручную (см. раздел 9).

Иначе попытка **отклоняется**. Причина (чьи ответы разошлись, какие issues) передаётся Генератору в следующую попытку. Методист заново не вызывается, ТЗ остаётся прежним.

- Лимит — 3 попытки. После них запуск считается неудачным: пишем в лог, ученику ничего не выдаём. Больше попыток не даём:
  - если модель не справилась после двух прицельных исправлений, дальше она обычно перебирает те же нерабочие варианты;
  - одна задача и так обходится максимум в 10 платных вызовов Claude (1 Методист + 3 × Генератор, Аналитик, Скептик);
  - отказ после 3 попыток сам по себе сигнал: по таблице `attempts` видно, на каких темах и ловушках модель спотыкается или где ТЗ Методиста противоречиво.
- Замечания `minor` сохраняются вместе с задачей для ручного разбора.

### Генератор ошибся в ответе

Особый случай: Аналитик и Скептик дали одинаковый ответ, он отличается от ответа Генератора, и у Скептика нет блокирующих issues. Значит, условие нормальное, а ошибся Генератор.

Просто подменить `correct_answer` на ответ верификаторов нельзя. У нового верного варианта в `distractors` останется описание ловушки (его покажут ученику, который ответил верно), у старого «верного» ловушки не будет, а `solution` приводит к неверному ответу.

Что делаем:

1. Попытке ставится статус `generator_answer_error`.
2. На следующей попытке Генератор не придумывает новую задачу, а исправляет эту. Он получает ответ верификаторов и должен, не меняя `question` и `options`, исправить `correct_answer`, `solution`, `distractors` и при необходимости `hint`: убрать ловушку у нового верного варианта и описать ловушку для старого.
3. Скрипт проверяет, что `question` и `options` не изменились. Верификаторов заново не вызываем: они уже решали именно это условие.
4. Исправление считается попыткой в общем лимите.

## 7. Что хранится в БД

Всё хранится в PostgreSQL (Docker-контейнер, `docker-compose.yml`, схема в `db/schema.sql`). Файлов с результатами нет.

| Таблица | Что внутри | Зачем |
|---|---|---|
| `students` | Профиль ученика: класс, интересы, `cognitive_profile`, `mastered_topics`, `excluded_skills`, `consecutive_failures` | Вход для Методиста |
| `student_tasks` | Выданные ученику задачи и его ответы: `correct`, `chosen_option`, `trap_hit`, `feedback`, `hint_used`, `pace` | История для Методиста (последние 5 записей) и защита от повторной выдачи |
| `tasks` | Банк: принятые задачи целиком — ТЗ, JSON Генератора, ответы Аналитика и Скептика, число попыток | Повторное использование (см. 5.5). Отсюда же беру задачи для ручной проверки качества |
| `requests` | Один запрос задачи: ученик, ТЗ Методиста, откуда задача (`bank`, `generated` или `failed`), число попыток, суммарные токены, стоимость и время | Метрики по задачам: доля из банка, цена и время одной задачи |
| `attempts` | Каждая попытка генерации, включая отклонённые: статус (`accepted`, `rejected` или `generator_answer_error`), причина отказа, ответы всех агентов, модели, токены, стоимость, время | Главный источник выводов по прототипу, в том числе на каких темах и ловушках задачи не проходят за 3 попытки |
| view `finetune_solver` | prompt: условие + варианты; completion: рассуждение Аналитика + ответ | Учить модель *решать* |
| view `finetune_generator` | prompt: ТЗ Методиста; completion: полный JSON Генератора, прошедший консенсус (после `generator_answer_error` — исправленная версия) | Учить модель *генерировать*. Приоритетный датасет: решать задачи открытые модели уже умеют, а придумывать задачи в стиле «Кенгуру» с продуманными ловушками — нет |

Датасеты — это view над `tasks`: в них попадают только принятые задачи, без дублей и без отдельной записи. Для дообучения view выгружается в JSONL. Отклонённые попытки остаются в `attempts`: это готовые примеры плохих задач, они тоже пригодятся.

```sql
CREATE TABLE students (
  student_id           text   PRIMARY KEY,
  grade                int    NOT NULL,
  interests            text[] NOT NULL,
  cognitive_profile    text[] NOT NULL,
  mastered_topics      text[] NOT NULL,
  excluded_skills      text[] NOT NULL,
  consecutive_failures int    NOT NULL DEFAULT 0
);

CREATE TABLE tasks (                -- банк задач
  task_id         text PRIMARY KEY,
  created_at      timestamptz NOT NULL DEFAULT now(),
  topic           text   NOT NULL,  -- id темы из topics.json
  difficulty      int    NOT NULL,  -- 3, 4 или 5 баллов
  grade_level     text   NOT NULL,  -- '1-2' или '3-4'
  setting         text,
  excluded_skills text[] NOT NULL,  -- запреты из ТЗ, под которое задача сгенерирована
  traps           text[] NOT NULL,
  brief           jsonb  NOT NULL,  -- ТЗ Методиста
  task            jsonb  NOT NULL,  -- JSON Генератора
  analyst         jsonb  NOT NULL,  -- ответ Аналитика, в том числе разбор для ученика
  skeptic         jsonb  NOT NULL,
  attempt_count   int    NOT NULL
);

CREATE TABLE student_tasks (        -- выданные задачи и ответы = история ученика
  id            bigserial PRIMARY KEY,
  student_id    text NOT NULL REFERENCES students,
  task_id       text REFERENCES tasks,  -- NULL у записей из стартового профиля
  topic         text NOT NULL,
  difficulty    int  NOT NULL,
  issued_at     timestamptz NOT NULL DEFAULT now(),
  correct       boolean,                -- NULL: «не понял» или ещё не ответил
  chosen_option text,
  trap_hit      text,
  feedback      text,
  hint_used     boolean NOT NULL DEFAULT false,
  pace          text,                   -- 'fast', 'normal' или 'struggled'
  UNIQUE (student_id, task_id)
);

CREATE TABLE requests (             -- один запрос задачи для ученика
  request_id    bigserial PRIMARY KEY,
  created_at    timestamptz NOT NULL DEFAULT now(),
  student_id    text  NOT NULL REFERENCES students,
  brief         jsonb NOT NULL,         -- ТЗ Методиста
  source        text  NOT NULL,         -- 'bank', 'generated' или 'failed'
  task_id       text  REFERENCES tasks, -- NULL, если 'failed'
  attempt_count int   NOT NULL DEFAULT 0,
  tokens        int,
  cost_usd      numeric(10, 4),
  duration_ms   int
);

CREATE TABLE attempts (             -- каждая попытка генерации
  attempt_id  bigserial PRIMARY KEY,
  request_id  bigint NOT NULL REFERENCES requests,
  attempt_no  int    NOT NULL,        -- 1–3
  status      text   NOT NULL,        -- 'accepted', 'rejected' или 'generator_answer_error'
  reason      text,                   -- почему отклонена
  generator   jsonb,
  analyst     jsonb,
  skeptic     jsonb,
  models      jsonb,
  tokens      int,
  cost_usd    numeric(10, 4),
  duration_ms int
);

CREATE VIEW finetune_solver AS      -- датасет решателя
  SELECT task_id,
         jsonb_build_object('question', task -> 'question', 'options', task -> 'options') AS prompt,
         analyst AS completion
  FROM tasks;

CREATE VIEW finetune_generator AS   -- датасет генератора
  SELECT task_id, brief AS prompt, task AS completion
  FROM tasks;
```

## 8. LLM

- В прототипе все агенты работают на Claude через API: так проще. Локальные модели — во второй фазе.
- Модель для каждого агента задаётся отдельно в `config.yaml`. Внутри Claude агенты по возможности на разных моделях: если все на одних весах, они ошибаются одинаково и одинаково «додумывают» недостающее в условии.

| Агент | Модель | Почему |
|---|---|---|
| Методист | Claude Haiku 4.5 | Быстрая и дешёвая. Разбирает историю ученика и выбирает тему из каталога, задачи сам не решает |
| Генератор | Claude Opus 5 | Нужны связный сюжет, продуманные ловушки и строгий JSON. Сильная модель экономит ретраи |
| Аналитик | Claude Sonnet 5, temperature 0 (если модель позволяет) | Его рассуждение идёт в датасет как эталон и в разбор для ученика, и он основной верификатор |
| Скептик | Claude Sonnet 5, свой промпт | Не та модель, что у Генератора: задачу не проверяют теми же весами, которые её написали |

```yaml
agents:
  tutor:     { provider: anthropic, model: claude-haiku-4-5-20251001 }
  generator: { provider: anthropic, model: claude-opus-5 }
  analyst:   { provider: anthropic, model: claude-sonnet-5, temperature: 0 }
  skeptic:   { provider: anthropic, model: claude-sonnet-5 }
max_attempts: 3
pace:                 # пороги для тега pace в режиме --answer, значения примерные
  fast_below_sec: 60
  struggled_above_sec: 180
```

- **Известное ограничение.** Все агенты из одного семейства и могут одинаково «додумывать» недостающее в условии. В прототипе с этим живём: такие пропуски ловит моя ручная проверка (метрика «Ложно принятые» в разделе 9). Скептик другого семейства — во второй фазе.
- Методист на Haiku — тоже гипотеза. Если его выбор выглядит слабым, сначала пробуем Sonnet 5 и только потом делаем выводы о самой идее: выбор задачи — первая цель прототипа.
- Тонкая обёртка `llm.call(agent, messages) -> dict` скрывает разницу между моделями и считает токены и стоимость. В прототипе нужен только Anthropic API. Во второй фазе локальные модели (vLLM, Ollama) подключаются через OpenAI-совместимый API с другим `base_url`.
- **Вторая фаза прототипа:** сначала перевести на локальные модели Методиста и Скептика (Скептика — из другого семейства, не Claude), потом Генератора и Аналитика. Прогнать те же профили и сравнить долю принятых задач и качество. Это и ответит на вопрос, нужен ли fine-tuning. Локальным моделям 7–14B нужна видеокарта с 12–16 ГБ VRAM или достаточный объём общей памяти (например, Mac).

### Бюджет

- **API Anthropic.** Отдельный баланс: подписка Claude Pro на запросы из скриптов не распространяется. Прежняя грубая оценка ($10–15 на 200–300 запусков) считалась только для Генератора, а теперь на Claude все 4 агента. Реальный ориентир считаю по первым 10–20 запускам: стоимость каждого вызова пишется в `attempts` и `requests`.
- **Время.** Самый долгий шаг — Генератор на Opus 5. Аналитик и Скептик идут параллельно (см. раздел 6).

## 9. Как понять, что прототип удался

| Метрика | Как считаем | Цель |
|---|---|---|
| Принято с 1-й попытки | `requests`: доля `generated` с `attempt_count = 1` среди запросов с генерацией | > 50% |
| Принято за ≤ 3 попытки | `requests`: `generated` / (`generated` + `failed`) | > 80% |
| Качество по ручной проверке | Я (не LLM) проверяю 20–30 принятых задач (см. «Кто проверяет качество» ниже): решаема, однозначна, похожа на «Кенгуру», подходит по возрасту, подсказка не выдаёт ответ, ловушки и разбор понятны ребёнку | > 90% |
| **Ложно принятые** | Прошли консенсус, но при ручной проверке оказались математически плохими: неверный ответ, неоднозначное условие, нет решения или верны несколько вариантов. Главная метрика верификаторов | 0 (не больше 2%) |
| Ошибки Генератора в собственном ответе | Доля попыток со статусом `generator_answer_error` в `attempts` | без цели, наблюдаем |
| Доля задач из банка | `requests`: доля `source = 'bank'` | без цели, наблюдаем |
| Какие поля профиля работают | Частота полей в `profile_fields_used` из `requests.brief` | без цели, наблюдаем |
| Адаптивность | 5 разных профилей → разные темы, сложность и ловушки с понятным обоснованием. В режиме `--answer` после ошибок Методист меняет цель, а свежий `trap_hit` виден в следующем ТЗ | да |
| Разнообразие | 20 задач на одну тему не повторяют друг друга по сюжету и идее (оцениваю я вручную) | > 80% уникальных сюжетов |
| Цена и время одной принятой задачи | Деньги по API и секунды с учётом ретраев, из `requests`. Только `generated`, без задач из банка | < $0.10 и < 45 с |

### Кто проверяет качество

Качество проверяю я, автор прототипа, вручную (не LLM): у меня большой опыт решения задач «Кенгуру» и тренировки ребёнка на них с хорошим результатом. Внешние эксперты на этапе прототипа не нужны.

Я просматриваю 20–30 принятых задач по критериям из таблицы выше: решаема, однозначна, похожа на «Кенгуру», подходит по возрасту, подсказка не выдаёт ответ, ловушки и разбор понятны ребёнку.

## 11. После прототипа

Как роли прототипа ложатся на сервисы MathTrail:

| В прототипе | В MathTrail |
|---|---|
| Профиль и история (`students`, `student_tasks`) | `profile-api` (+ pgvector). Там автоматически считаются `pace`, `consecutive_failures`, `mastered_topics` и сводка истории, а `cognitive_profile` обновляется по `trap_hit` |
| Банк задач и журналы (`tasks`, `requests`, `attempts`) | БД задач в целевой системе |
| Методист | `mentor-api` |
| Цикл «Генератор → верификаторы → ретрай» | `task-api` (оркестрация) + `llm-taskgen` (вызовы LLM) |
| Цикл `--answer` (ответ → обновление профиля) | `solution-validator` (проверка ответа) + `profile-api` (обновление истории) |
| Аналитик и Скептик | внутри `llm-taskgen` или в `solution-validator` **[решить]**: он пока задуман для проверки решений ученика, а не сгенерированных задач |

Дальнейшие шаги:

1. Перенести промпты и JSON-схемы в `llm-taskgen` и `mentor-api`, в `contracts`.
2. Перевести агентов на локальные модели (см. «Вторая фаза» в разделе 8) и оценить разрыв с Claude.
3. Если разрыв большой, дообучить локальные модели (LoRA) на собранных датасетах. Если ресурсов хватит только на одну модель, начинаем с генератора. Перед этим проверить условия использования Anthropic: они могут ограничивать обучение других моделей на ответах Claude, а оба датасета собраны из ответов Claude.
4. Добавить задачи с рисунками: SVG или генерация картинок, плюс проверка рисунка верификаторами.
5. Выбрать, как ученик даёт обратную связь: кнопка «не понимаю», видео (по лицу видно, что трудно или непонятно), разговор голосом или текст.
6. Разбор ошибок отдельным LLM-вызовом по конкретному ответу ученика — в `mentor-api`.
7. Семантическая память ученика. Когда записей в `cognitive_profile` и отзывов (`feedback`) станут сотни, хранить их с эмбеддингами в pgvector. Генератору по выбранной теме подавать 3–4 самые близкие прошлые ошибки ученика, чтобы строить ловушки.

# llm-taskgen-prototype — что я хочу проверить

> Рабочий черновик. Места с пометкой **[решить]** — открытые, их надо поправить или вычеркнуть.
> Сводный список открытых вопросов — в разделе 12.

## 1. Зачем этот прототип

**Гипотеза:** цепочка LLM-агентов по профилю ученика может сама решить, какую задачу ему дать дальше, и сгенерировать решаемую, однозначную олимпиадную задачу в стиле «Кенгуру» для 1–4 классов.

**Язык:** задачи, промпты агентов и все данные только на английском. Сам этот документ остаётся на русском.

**Формат:** только текстовые задачи, без рисунков.

Что конкретно проверяю:

1. **Выбор задачи.** Методист по «сырому» профилю (история решений, ошибки, интересы) осмысленно выбирает тему, сложность и цель следующей задачи.
2. **Генерация.** Генератор по этому ТЗ делает задачу, похожую на «Кенгуру»: короткий сюжет, нестандартная идея, 5 вариантов ответа с продуманными ловушками.
3. **Верификация.** Два независимых верификатора отсеивают нерешаемые и неоднозначные задачи.
4. **Цена.** Сколько стоит и сколько длится получение одной хорошей задачи (токены, время, число попыток).

**Побочный продукт:** датасет «условие → пошаговое решение» (и, возможно, «ТЗ → задача») для будущего дообучения локальной модели.

Код одноразовый. После проверки гипотезы он выбрасывается, в основную систему переносятся промпты, схемы данных и выводы.

## 2. Что НЕ входит в прототип

- k8s, Kafka, Go, воркеры, очереди.
- PostgreSQL / pgvector: профиль и история хранятся в JSON-файлах.
- UI: только консоль.
- Fine-tuning: только собираем для него данные.
- Реальные ученики: профили выдуманные.
- Задачи с рисунками: в прототипе только текстовые задачи.
- Способ, которым ученик даёт обратную связь (кнопка «не понимаю», видео, голос, текст). В прототипе это просто поле `feedback` в истории профиля.

## 3. Как это выглядит при запуске

```bash
python main.py --profile profiles/masha.json
```

1. Скрипт читает профиль ученика.
2. **Методист** выдаёт ТЗ на задачу, оно печатается в консоль.
3. **Генератор → Аналитик + Скептик**, до 3 попыток.
4. В консоли итоговая задача, варианты, правильный ответ, решение и сводка: сколько было попыток, токенов, денег, секунд.
5. В `output/` пишутся файлы из раздела 7.

**[решить]** Режим `--answer`: я отвечаю за ученика, ответ дописывается в историю профиля, и следующий запуск видит уже обновлённый профиль. Без этого режима адаптивность можно проверить только на статичных профилях, а не на цепочке «задача → ответ → следующая задача».

## 4. Входные данные

### 4.1 Профиль ученика

```json
{
  "id": "masha",
  "grade": 3,
  "interests": ["space", "robots"],
  "cognitive_profile": [
    "doesn't read long questions to the end and loses interest",
    "off-by-one when counting gaps",
    "misses the word \"not\" in the question"
  ],
  "mastered_topics": ["logic.knights_liars"],
  "excluded_skills": ["division with remainder", "fractions"],
  "consecutive_failures": 2,
  "history": [
    {
      "task_id": "t-0012",
      "topic": "logic.knights_liars",
      "difficulty": 3,
      "correct": true,
      "pace": "fast"
    },
    {
      "task_id": "t-0013",
      "topic": "combinatorics.enumeration",
      "difficulty": 4,
      "correct": false,
      "chosen_option": "B",
      "trap_hit": "missed one case while enumerating",
      "pace": "struggled"
    },
    {
      "task_id": "t-0014",
      "topic": "time.clocks",
      "difficulty": 3,
      "correct": null,
      "feedback": "didn't understand the question",
      "pace": "struggled"
    }
  ]
}
```

| Поле | Что это | В прототипе | В целевой системе |
|---|---|---|---|
| `grade` | Класс ученика | вручную | из профиля |
| `interests` | Интересы, из них Методист берёт сеттинг | вручную | из профиля |
| `cognitive_profile` | Устойчивые особенности и типичные ошибки ученика, одним списком | вручную | обновляется автоматически по `trap_hit` (фоновый процесс или Методист в конце сессии) |
| `mastered_topics` | id тем из `topics.json`, которые ученик уже закрыл. Нужны, чтобы при `new_topic` не ходить по кругу | вручную | бэкенд по истории |
| `excluded_skills` | Чего ученик ещё не проходил в школе. Нельзя использовать ни в условии, ни в ловушках | вручную | вручную или по школьной программе класса |
| `consecutive_failures` | Сколько задач подряд не решено (неверный ответ или «не понял»). Помогает Методисту вовремя выбрать `motivate` | вручную | бэкенд |
| `history` | 3–5 последних задач | вручную | 3–5 последних задач плюс сводка успеваемости вместо полной истории |
| `history[].pace` | Темп: `fast`, `normal` или `struggled`. Секунды LLM не с чем сравнить, поэтому передаём готовый тег | вручную | бэкенд по времени решения и норме для класса |
| `history[].trap_hit` | Какую ловушку поймал ученик (см. ниже) | вручную | по разметке `distractors` Генератора |
| `history[].feedback` | Обратная связь ученика по задаче, например «не понимаю» | вручную | канал обратной связи (см. раздел 13) |

- `trap_hit` берётся из разметки ловушек Генератора (см. 5.2). Если ученик выбрал B, а Генератор пометил B как «missed one case while enumerating», значит, мы знаем, какую именно ошибку он сделал. Эта связка, по-моему, самое ценное в профиле.
- Правил по классам (вроде «для 1 класса условие короче») нет. Методист подстраивает длину и сложность формулировки под конкретного ученика по его истории, `cognitive_profile` и `feedback` и передаёт это Генератору в `constraints`.

### 4.2 Каталог тем

`topics.json` — плоский список тем 1–4 классов с id и коротким описанием. Методист выбирает тему **из каталога**, а не придумывает её сам, иначе историю разных учеников и запусков нельзя будет сравнить.

Черновой список **[решить]**:

- Арифметика с хитростью: удобный порядок действий, «задумал число».
- Логика: рыцари и лжецы, упорядочивание («кто выше», «кто за кем»), истинные и ложные утверждения.
- Перебор вариантов: маршруты, рукопожатия, составление чисел из цифр.
- Время: часы, календарь, возраст.
- Промежутки и заборы (ловушка ±1).
- Взвешивания и переливания.
- Чётность.
- Простейший принцип Дирихле.
- Закономерности в последовательностях.
- Геометрия, описанная словами: периметр, клетчатые фигуры без рисунка.

### 4.3 Эталонные задачи (few-shot)

`examples/kangaroo.json` — 10–15 задач «Кенгуру» из англоязычных выпусков (Math Kangaroo). У каждой размечены тема, класс, баллы, правильный ответ и короткое решение. Генератору подаём 3–5 примеров, близких к теме ТЗ. Отбираем простым фильтром по теме, без векторного поиска.

**Шкала сложности.** В «Кенгуру» задачи стоят 3, 4 или 5 баллов. Берём эти баллы как готовую шкалу сложности (`difficulty`).

## 5. Агенты

```
  [Профиль ученика] + [Каталог тем]
            │
            ▼
     ┌─────────────┐
     │  Методист   │ → ТЗ: тема, сложность, цель, сеттинг, ловушки
     └─────────────┘
            │
            ▼
     ┌─────────────┐ ◄── 3–5 эталонных задач
     │  Генератор  │ → условие, варианты A–E, задуманный ответ X, решение
     └─────────────┘
            │   (дальше уходят только условие и варианты)
     ┌──────┴───────────┐
     ▼                  ▼
┌───────────┐     ┌───────────┐
│ Аналитик  │     │  Скептик  │  (желательно другая модель)
│ ответ Y   │     │ ответ Z   │
│           │     │ + issues  │
└───────────┘     └───────────┘
     └──────┬───────────┘
            ▼
   X == Y == Z и нет блокирующих issues?
     ├─ да  → выдаём задачу + пишем в датасет
     └─ нет → новая попытка Генератора (до 3) с причиной отказа
```

### 5.1 Методист (Tutor)

**Роль:** решает, *что* дать ученику прямо сейчас.
**Вход:** профиль, каталог тем.
**Выход:**

```json
{
  "rationale": "Two failures in a row: missed a case in enumeration, then didn't understand a clocks question. Give an easier, short enumeration task to rebuild confidence.",
  "pedagogical_goal": "motivate",
  "target_concept": "combinatorics.enumeration",
  "difficulty": 3,
  "setting": "space",
  "traps_to_use": ["missed one case while enumerating", "double counting"],
  "constraints": ["question no longer than 3 sentences"],
  "excluded_skills": ["division with remainder", "fractions"]
}
```

`pedagogical_goal` принимает одно из трёх значений: `reinforce` (закрепить слабое место), `motivate` (дать задачу полегче для уверенности) или `new_topic` (перейти к новой теме).

`excluded_skills` Методист переносит из профиля в ТЗ, чтобы Генератор не использовал эти навыки ни в условии, ни в ловушках.

### 5.2 Генератор

**Роль:** придумывает задачу по ТЗ.
**Вход:** ТЗ от Методиста; 3–5 эталонных задач; последние задачи ученика, чтобы не повторяться; на повторной попытке — причина, по которой отклонили прошлую.
**Выход:**

```json
{
  "design_thought_process": "Plot: spaceships docking. Count the pairs, the answer is 6. Trap 5: one pair missed. Trap 12: every pair counted twice.",
  "question": "…",
  "options": {"A": "4", "B": "5", "C": "6", "D": "8", "E": "12"},
  "correct_answer": "C",
  "solution": "…",
  "distractors": {
    "A": "…",
    "B": "missed one pair while enumerating",
    "D": "…",
    "E": "every pair counted twice"
  }
}
```

`distractors` нужен, чтобы по неверному ответу ученика понять его ошибку (поле `trap_hit` в профиле).

### 5.3 Аналитик (верификатор 1)

**Роль:** честно решает задачу вслепую.
**Вход:** только `question` и `options`. Задуманный ответ и решение Генератора он не видит.
**Настройки:** минимальная случайность (temperature 0, если модель это позволяет).
**Выход:**

```json
{
  "solving_thought_process": "Step 1: … Step 2: … So there are 6 pairs.",
  "final_answer": "C"
}
```

Его рассуждение потом попадает в датасет для обучения решателя.

### 5.4 Скептик (верификатор 2)

**Роль:** ищет, почему задача *плохая*, и только после этого решает её.
**Вход:** те же `question` и `options`.
**Модель:** желательно другая модель или другой провайдер (см. раздел 11, «Общие ошибки одной модели»).
**Выход:**

```json
{
  "issues": [
    {"type": "ambiguous", "severity": "blocking", "comment": "Unclear whether pairs A–B and B–A count as different."}
  ],
  "option_check": {
    "A": "wrong because …",
    "B": "wrong because …",
    "C": "correct",
    "D": "wrong because …",
    "E": "wrong because …"
  },
  "final_answer": "C"
}
```

- Возможные `type` в `issues`: `ambiguous`, `missing_data`, `multiple_correct`, `no_correct`, `too_hard_for_grade`, `needs_picture`, `factual_error`.
- `severity`: `blocking` (задачу отклоняем) или `minor` (задачу оставляем, замечание сохраняем).
- `option_check` проверяет, что верен ровно один вариант.
- Если решить задачу нельзя, `final_answer` = `"UNSOLVABLE"`.

## 6. Консенсус и ретраи

Задача **принимается**, если:

1. JSON всех агентов валиден, вариантов ровно 5, и все они разные;
2. ответ Генератора == ответ Аналитика == ответ Скептика;
3. у Скептика нет issues с `severity: blocking`.

Иначе попытка **отклоняется**. Причина (чьи ответы разошлись, какие issues) передаётся Генератору в следующую попытку. Методист заново не вызывается, ТЗ остаётся прежним.

- Лимит — 3 попытки **[решить]**. После них запуск считается неудачным: пишем в лог, ученику ничего не выдаём.
- Замечания `minor` сохраняются вместе с задачей для ручного разбора.
- **[решить]** Аналитик и Скептик сошлись между собой, но не с Генератором. Скорее всего, задача нормальная, просто Генератор ошибся в ответе. Пока отклоняем (так строже), но такие случаи считаем отдельно.

## 7. Выходные артефакты

| Файл | Что внутри | Зачем |
|---|---|---|
| `output/tasks/<время>_<профиль>.json` | Принятая задача целиком: ТЗ, ответы всех агентов, число попыток | Смотреть глазами, проверять качество |
| `output/runs.jsonl` | Каждая попытка, включая отклонённые: причина отказа, модели, токены, стоимость, время | Главный источник выводов по прототипу |
| `output/finetune_solver.jsonl` | prompt: условие + варианты; completion: рассуждение Аналитика + ответ | Учить модель *решать* |
| `output/finetune_generator.jsonl` **[решить]** | prompt: ТЗ Методиста; completion: задача от Генератора | Учить модель *генерировать*. Для MathTrail это, возможно, важнее решателя |

Отклонённые попытки не удаляем: это готовые примеры плохих задач, они тоже пригодятся.

## 8. LLM

- Прототип делаем на облачных моделях: проверяем идею, а не пределы слабой модели.
- Gemini советовал Claude 3.5 Sonnet и GPT-4o, но это старые модели. Сейчас (сентябрь 2026) актуальны Claude Opus 5 / Sonnet 5 / Haiku 4.5 и их аналоги у других провайдеров.
- Модель для каждого агента задаётся отдельно в `config.yaml`:

```yaml
agents:
  tutor:     { provider: anthropic, model: claude-sonnet-5 }
  generator: { provider: anthropic, model: claude-opus-5 }
  analyst:   { provider: anthropic, model: claude-sonnet-5, temperature: 0 }
  skeptic:   { provider: <другой провайдер>, model: <другая модель> }
max_attempts: 3
```

- Тонкая обёртка `llm.call(agent, messages) -> dict` скрывает разницу между провайдерами и считает токены и стоимость. Локальные модели (vLLM, Ollama) подключаются через OpenAI-совместимый API с другим `base_url`.
- **Вторая фаза прототипа:** прогнать те же профили на локальной модели и сравнить долю принятых задач и качество. Это и ответит на вопрос, нужен ли fine-tuning.

## 10. Структура кода

```
main.py                — CLI и цикл попыток
agents.py              — tutor(), generator(), analyst(), skeptic()
llm.py                 — обёртка над провайдерами, учёт токенов и стоимости
prompts/               — tutor.md, generator.md, analyst.md, skeptic.md
profiles/*.json        — 3–5 выдуманных учеников с разной историей
examples/kangaroo.json — эталонные задачи
topics.json            — каталог тем
config.yaml            — модели по агентам, лимиты
output/                — результаты (в .gitignore)
```

Без агентных фреймворков (LangChain и т. п.): четыре последовательных вызова проще и понятнее написать руками.

## 11. Замечания и риски

Здесь я поправляю или уточняю выводы из разговора с Gemini.

- **Совпадение ответов ≠ хорошая задача.** Три одинаковые буквы не гарантируют, что условие однозначно, что остальные варианты неверны и что задача подходит по возрасту и интересна. Поэтому у Скептика есть `issues` и `option_check`, и нужна ручная проверка.
- **Общие ошибки одной модели.** Если все агенты работают на одной модели, они одинаково «додумают» недостающее в условии. Скептик на той же модели мало что добавит, поэтому лучше отдать его другой модели.
- **Стоимость.** Датасет не бесплатный: минимум 4 вызова на задачу плюс ретраи, а Генератор работает на самой дорогой модели. Считаем стоимость с первого прогона.
- **Дистилляция и условия провайдеров.** Условия использования облачных моделей могут ограничивать обучение других моделей на их ответах. Проверить это до того, как строить план на дообучении.
- **Авторские права.** Реальные задачи «Кенгуру» можно использовать в промптах как образец стиля, но в датасет их не кладём.
- **RAG или fine-tuning.** Gemini прав: сотня задачников в векторной базе не научит модель рассуждать. Но поиск похожих задач полезен как источник few-shot примеров. В прототипе это простой фильтр по теме.
- **Повторы.** Модель склонна повторять одни и те же сюжеты. Поэтому Генератору передаём последние задачи ученика, а в метриках отдельно смотрим разнообразие.

## 13. После прототипа

Как роли прототипа ложатся на сервисы MathTrail:

| В прототипе | В MathTrail |
|---|---|
| Профиль (JSON-файл) | `profile-api` (+ pgvector). Там автоматически считаются `pace`, `consecutive_failures`, `mastered_topics` и сводка истории, а `cognitive_profile` обновляется по `trap_hit` |
| Методист | `mentor-api` |
| Цикл «Генератор → верификаторы → ретрай» | `task-api` (оркестрация) + `llm-taskgen` (вызовы LLM) |
| Аналитик и Скептик | внутри `llm-taskgen` или в `solution-validator` **[решить]**: он пока задуман для проверки решений ученика, а не сгенерированных задач |

Дальнейшие шаги:

1. Перенести промпты и JSON-схемы в `llm-taskgen` и `mentor-api`, в `contracts`.
2. Прогнать прототип на локальной модели и оценить разрыв с облачной.
3. Если разрыв большой, дообучить локальную модель (LoRA) на собранном датасете.
4. Добавить задачи с рисунками: SVG или генерация картинок, плюс проверка рисунка верификаторами.
5. Выбрать, как ученик даёт обратную связь: кнопка «не понимаю», видео (по лицу видно, что трудно или непонятно), разговор голосом или текст.

# llm-taskgen-prototype — что я хочу проверить

> Рабочий черновик. Места с пометкой **[решить]** — открытые, их надо поправить или вычеркнуть.

## 1. Зачем этот прототип

**Гипотеза:** MCP-сервер с профилем ученика, рейтингами, эталонными задачами и проверками позволяет модели самого AI-клиента (Claude, ChatGPT и других) прямо в чате выбрать, какую задачу дать ученику, и написать решаемую, однозначную олимпиадную задачу для 1–4 классов с пятью вариантами ответа. Своих вызовов LLM у нас нет.

**Как это устроено.** Ученик разговаривает со своим AI-клиентом. Наш сервер подключён к клиенту как MCP-коннектор и даёт ему инструменты: профиль, следующая задача, приём задачи, приём ответа, прогресс (5.8). Текст задачи пишет модель клиента в рамках подписки пользователя, а сервер отдаёт данные, рекомендацию и эталоны и проверяет всё, что модель прислала. Для нас стоимость LLM — ноль, платим только за свою инфраструктуру (D42). Готовые задачи копятся в банке и выдаются повторно другим ученикам без генерации.

**Язык:** код, инструкции сервера для модели (`prompts/`) и все данные — на английском. Задачи для ребёнка модель пишет на языке чата, язык хранится вместе с задачей. Сам этот документ остаётся на русском.

**Формат:** только текстовые задачи, без рисунков, с пятью вариантами ответа A–E. В олимпиадах для младших школьников много задач с рисунком (в крупном международном конкурсе — 60–70%, research/02), так что прототип проверяет генерацию только текстовой части.

**Ориентир стиля:** олимпиадные задачи и задачи разного уровня сложности из советских сборников. Формулировки задач из книг не копируем (4.3).

Что конкретно проверяю:

1. **Выбор задачи.** Модель клиента по профилю (история решений, ошибки, интересы), коридору сложности и рекомендации правила (5.7) осмысленно выбирает тему, сложность и цель следующей задачи — и делает это лучше самого правила.
2. **Генерация.** Модель клиента по ТЗ и эталонам пишет олимпиадную задачу: короткий сюжет, нестандартная идея, 5 вариантов ответа с продуманными ловушками.
3. **Проверка.** Проверки сервера (раздел 6) — структура, программа-решатель в песочнице, самопроверка по чек-листу, читаемость, близкие дубли — отсеивают нерешаемые и неоднозначные задачи, хотя задачу пишет и проверяет одна и та же модель.
4. **Опыт ученика.** Сколько попыток и секунд уходит на одну принятую задачу и насколько естественно всё выглядит в чате.

**Побочный продукт:** датасеты «ТЗ → задача» и «условие → решение» (view в разделе 7). Дообучать на них не будем: это ответы моделей AI-клиентов, их условия использования не разрешают брать ответы как обучающие цели (research/08). Они нужны как эталон для оценки других моделей (раздел 11).

Код одноразовый. После проверки гипотезы он выбрасывается, в основную систему переносятся инструменты, инструкции, схемы данных и выводы.

## 2. Что НЕ входит в прототип

- k8s, Kafka, Go, воркеры, очереди.
- Свои вызовы LLM API (Anthropic, OpenAI и других): текст пишет модель клиента (D42).
- Удалённый сервер, хостинг и OAuth: в прототипе сервер работает локально и подключается к Claude Code (8, 11).
- Свой интерфейс: только чат клиента. Интерактивная карточка задачи (MCP Apps) — после прототипа (11).
- pgvector: всё хранится в PostgreSQL (раздел 7), но поиск по смыслу не используем.
- Fine-tuning: не делаем. Собранные датасеты для обучения не используем (см. раздел 1).
- Реальные ученики: профили выдуманные.
- Задачи с рисунками: в прототипе только текстовые задачи.
- Способ, которым ученик даёт обратную связь (кнопка «не понимаю», видео, голос, текст). В прототипе это просто поле `feedback` в истории профиля.

## 3. Как это выглядит при запуске

```bash
docker compose up -d                         # PostgreSQL (раздел 7)
python -m taskgen.apply_schema               # один раз: схема БД
python -m taskgen.seed                       # один раз: стартовые профили из data/seed/*.json
claude                                       # Claude Code в папке проекта подхватывает MCP-сервер из .mcp.json
```

Автор играет ученика в Claude Code. Типичный разговор:

1. Ученик пишет в чате, например: «Я masha, дай мне задачу». Ученик задаётся псевдонимом (`student_id`, 4.1).
2. Модель смотрит `get_student_profile`: там коридор сложности по темам (5.6) и ТЗ-рекомендация правила (5.7). Затем вызывает `get_next_task` — по рекомендации или со своей темой и сложностью и причиной (5.1). Сервер ищет готовую задачу в банке (5.5). Нашлась задача, которую ученик ещё не получал, — сервер выдаёт её ученику и отдаёт модели условие, варианты и подсказку, но не ответ; модель показывает условие и варианты.
3. Не нашлась — сервер возвращает модели пакет: ТЗ, коридор, описания темы, ловушек и запрещённых навыков, 3 эталонные задачи, форматы и руководство с чек-листом самопроверки. Модель пишет задачу и программу-решатель, проверяет себя по чек-листу и вызывает `submit_task`; сюжет, ловушки и ограничения ТЗ она может уточнить.
4. Сервер проверяет задачу (раздел 6). Принята — задача попадает в банк и выдаётся ученику, модель показывает условие и варианты, но не ответ. Отклонена — модель получает все причины и исправляет задачу, до 3 попыток на запрос.
5. Ученик отвечает буквой, пишет «не понимаю» или просит подсказку (`hint` из задачи). Модель вызывает `submit_answer`. Сервер сравнивает ответ с верным и сохраняет в историю:
   - верный ответ → `correct: true`;
   - неверный → `correct: false`, `chosen_option` и `trap_hit` = `distractors[выбранная буква].trap`;
   - «не понимаю» → `correct: null`, `feedback: "didn't understand the question"`;
   - `hint_used: true`, если ученик брал подсказку;
   - `pace` — по времени от выдачи задачи до ответа (время подсказки входит), с порогами из `config.yaml`.

   Затем сервер обновляет `consecutive_failures` и рейтинги (5.6) и возвращает модели, верен ли ответ, текст ловушки выбранного варианта и решение. Модель объясняет ученику.
6. «Покажи мой прогресс» → `get_progress`: рейтинги по темам, освоенные темы, последние ответы.

`consecutive_failures` обнуляется после верного ответа и растёт на 1 после неверного или «не понимаю»; подсказка неудачей не считается. Меняются только история ответов, `consecutive_failures` и рейтинги; `cognitive_profile` и `mastered_topics` не меняются.

Если задача не прошла за 3 попытки, запрос считается неудачным, модель сообщает об этом и может сразу попросить новую задачу. Всё пишется в БД сразу: следующий разговор продолжает с того места, где остановился прошлый, и ученик не получит повторно ту же задачу. Чтобы начать эксперимент заново, ученика сбрасывают командой `python -m taskgen.seed`.

**Известное ограничение прототипа.** Верный ответ есть в контексте модели и в параметрах вызова `submit_task`, а клиент показывает вызовы инструментов: любопытный ребёнок может его подсмотреть. Скрыть ответ поможет карточка задачи в MCP Apps (раздел 11).

**Зачем чат, а не консоль.** Разговор с моделью и есть симуляция ученика: видно, как модель меняет цель после ошибок (`new_topic` → `reinforce` → `motivate`), как свежий `trap_hit` отражается в следующем ТЗ и как проходит разбор ошибки.

## 4. Входные данные

### 4.1 Профиль ученика

Профиль хранится в БД, в таблицах `students` и `student_tasks` (раздел 7). Стартовые профили я пишу руками в JSON в формате ниже (`data/seed/*.json`) и загружаю в БД командой `python -m taskgen.seed`. `history` при загрузке превращается в строки `student_tasks`.

Состав профиля — гипотеза. Какие поля реально важны, покажет прототип (см. `profile_fields_used` в 5.1).

```json
{
  "id": "masha",
  "grade": 3,
  "interests": ["space", "robots"],
  "cognitive_profile": [
    "doesn't read long questions to the end and loses interest",
    "off-by-one when counting gaps",
    "misses the word \"not\" in the question"
  ],
  "mastered_topics": ["logic.knights_liars"],
  "excluded_skills": ["division_with_remainder", "fractions"],
  "consecutive_failures": 2,
  "history": [
    {
      "topic": "logic.knights_liars",
      "difficulty": 2,
      "correct": true,
      "pace": "fast"
    },
    {
      "topic": "combinatorics.enumeration",
      "difficulty": 3,
      "correct": false,
      "chosen_option": "B",
      "trap_hit": "missed_case",
      "hint_used": true,
      "pace": "struggled"
    },
    {
      "topic": "time.clocks",
      "difficulty": 2,
      "correct": null,
      "feedback": "didn't understand the question",
      "pace": "struggled"
    }
  ]
}
```

| Поле | Что это | В прототипе | В целевой системе |
|---|---|---|---|
| `grade` | Класс ученика | вручную | из профиля |
| `interests` | Интересы, из них берётся сеттинг | вручную | из профиля |
| `cognitive_profile` | Устойчивые особенности и типичные ошибки ученика, одним списком | вручную | обновляется автоматически по `trap_hit` (фоновый процесс или модель в конце сессии) |
| `mastered_topics` | id тем из `topics.json`, которые ученик уже закрыл. Нужны, чтобы при `new_topic` не ходить по кругу | вручную | бэкенд по истории |
| `excluded_skills` | id навыков из `skills.json` (см. 4.4), которых ученик ещё не проходил в школе. Нельзя использовать ни в условии, ни в ловушках | вручную | вручную или по школьной программе класса |
| `consecutive_failures` | Сколько задач подряд не решено (неверный ответ или «не понял»). Помогает вовремя выбрать `motivate` | вручную | бэкенд |
| `history` | Все выданные ученику задачи и его ответы, без ограничения. Модели передаются последние 5 | стартовые записи вручную, дальше пишет сервер | все задачи; модели — последние записи плюс сводка успеваемости |
| `history[].pace` | Темп: `fast`, `normal` или `struggled`. Секунды модели не с чем сравнить, поэтому передаём готовый тег | вручную | бэкенд по времени решения и норме для класса |
| `history[].trap_hit` | id ловушки из `traps.json` (см. 4.5), которую поймал ученик | вручную | по разметке `distractors` задачи |
| `history[].feedback` | Обратная связь ученика по задаче, например «не понимаю» | вручную | канал обратной связи (см. раздел 11) |
| `history[].hint_used` | Брал ли ученик подсказку | вручную | по действиям ученика |

Колонка «В прототипе» относится к стартовому профилю. Дальше новые записи истории и `consecutive_failures` пишет сервер (`submit_answer`, 5.8). Рейтинги (5.6) в стартовом профиле не задаются: `seed.py` считает их (общий уровень и поправки по темам), прогоняя стартовую историю.

В стартовой истории нет `task_id`: этих задач нет в банке, поэтому `student_tasks.task_id` у таких записей пустой (раздел 7). Записи идут от старых к новым. `consecutive_failures` должен совпадать с числом неудач подряд в конце истории, `seed.py` это проверяет.

**Только псевдонимы.** В профиле и в том, что сервер отдаёт модели, — только id вроде `masha`: никаких реальных имён, дат рождения, школ. `cognitive_profile` — чувствительное описание ребёнка: он уходит модели клиента только затем, чтобы подобрать задачу, и больше никуда не логируется (research/10).

Как хранятся поля:

- `grade`, `consecutive_failures`, `mastered_topics`, `excluded_skills`, `interests` — обычные колонки и массивы, только точное сравнение. Векторы здесь вредны: поиск по смыслу может счесть запрещённый навык «похожим» на разрешённый.
- `cognitive_profile` — в прототипе массив строк, модель получает его целиком. Когда записей станут сотни, понадобится семантическая память (см. раздел 11).

- `trap_hit` берётся из разметки ловушек задачи (см. 5.2). Если ученик выбрал B, а в задаче B помечен ловушкой `missed_case`, значит, мы знаем, какую именно ошибку он сделал. Эта связка, по-моему, самое ценное в профиле. По одному `trap_hit` далеко идущих выводов не делаем: без штрафа за ошибку дети часто угадывают.
- Правил по классам (вроде «для 1 класса условие короче») нет. Модель подстраивает длину и сложность формулировки под конкретного ученика по его истории, `cognitive_profile` и `feedback` и записывает это в `constraints` ТЗ.

### 4.2 Каталог тем

`topics.json` — плоский список тем 1–4 классов с id и коротким описанием. Тема выбирается **из каталога**, модель её не придумывает, иначе историю разных учеников и запусков нельзя будет сравнить.

Главный фильтр — только текстовые задачи. Тема должна однозначно формулироваться словами, без рисунка и без пространственного воображения: с дискретной логикой и перебором модели справляются хорошо, а геометрию «в уме» представляют ненадёжно.

**Берём:**

| id | Тема | Примеры |
|---|---|---|
| `logic.ordering` | Упорядочивание | кто за кем стоит, кто старше или выше |
| `logic.knights_liars` | Рыцари и лжецы, истинные и ложные утверждения | |
| `combinatorics.enumeration` | Перебор вариантов | рукопожатия, простые маршруты, описанные словами, числа из заданных цифр |
| `counting.gaps` | Промежутки и границы (ловушка ±1) | распилы брёвен, деревья в ряд, этажи |
| `time.clocks` | Часы | разница во времени |
| `time.calendar` | Календарь и возраст | сдвиг дней недели, возраст через несколько лет |
| `pigeonhole.basic` | Простейший принцип Дирихле | сколько носков вытащить в темноте, чтобы точно была пара |
| `parity.alternation` | Чётность и чередование | свойства чисел, чередование в последовательности |
| `arithmetic.tricks` | Арифметика с хитростью | удобный порядок действий, «задумал число» |
| `algorithms.weighing_pouring` | Взвешивания и переливания | |

Все темы из списка вычислимы перебором — на этом держится программная проверка (5.3).

**Исключаем:**

- **Пространственная геометрия:** развёртки кубиков, перекатывание кубика, оригами (складывание и разрезание бумаги). Без рисунка условие выходит либо неоднозначным, либо длинным и сухим, а не короткой олимпиадной задачей.
- **Визуальный подсчёт:** «сколько треугольников на картинке», наложение фигур.
- **Симметрия и зеркальные отражения:** оси симметрии в текстовом описании понимаются по-разному.
- **Геометрия, описанная словами:** периметр, клетчатые фигуры. Та же проблема, что с пространственной геометрией.
- **Тяжёлая арифметика и дроби:** не олимпиадный формат для 1–4 классов и провоцирует вычислительные ошибки модели.
- **Школьные задачи на движение и работу:** встречные поезда, трубы и бассейн. Это школьная рутина, а не олимпиадная логика.
- **Закономерности в последовательностях** (`patterns.sequences`): у последовательности почти всегда несколько правдоподобных продолжений, и программа не докажет, что правило единственное. Это классический источник неоднозначности (research/05).

### 4.3 Эталонные задачи (few-shot)

`data/examples/<тема>.json` — 450 задач: по 5 на каждую тройку «тема × уровень класса × сложность 1–5». **Написаны Claude в T11 по моей просьбе, проверяю их я.** Ориентир стиля — олимпиадные задачи и задачи разного уровня сложности из советских сборников (research/12); формулировки из книг не копируются: идеи задач авторским правом не охраняются, текст охраняется. Ответ каждой задачи проверен перебором на Python (`tests/example_checks/`) и слепым решением другой моделью. У каждой размечены тема, уровень класса, сложность, правильный ответ, короткое решение и **ловушка каждого неверного варианта** (id из `traps.json`, 4.5): по данным Eedi, похожие задачи с размеченными ловушками дают лучшие дистракторы (research/04).

`get_next_task` отдаёт модели 3 эталона по теме ТЗ, в первую очередь того же уровня класса и сложности. Отбираем простым фильтром, без векторного поиска. Эталоны на английском, а задачу модель пишет на языке чата: эталоны задают идею, структуру и разметку ловушек, а не язык.

**Чужие формулировки задач не используем нигде** — ни в инструкциях, ни в датасетах: ни из книг, ни из открытых наборов; из источника берём только идею. Свободно доступная книга не обязательно находится в общественном достоянии, а открытые наборы задач конкурсов (MathArena) разрешены только для некоммерческого использования, а SMART-840 ещё и прямо запрещает обучение ИИ на своих задачах (research/02).

**Шкала сложности.** `difficulty` — сложность от 1 (самая лёгкая) до 5 (самая трудная). Она считается внутри уровня класса: задача сложности 3 для 1–2 и для 3–4 класса — разные задачи.

### 4.4 Каталог навыков

`skills.json` — закрытый список школьных навыков с id и коротким описанием: `multiplication`, `division_with_remainder`, `fractions` и т. д. `excluded_skills` в профиле и в ТЗ ссылается только на id из этого каталога, как `mastered_topics` — на `topics.json`. Иначе точное сравнение в банке задач (5.5) не сработает: «fractions» и «simple fractions» для него разные навыки.

### 4.5 Каталог ловушек

`traps.json` — закрытый список типичных ловушек с id и коротким описанием. `traps_to_use` в ТЗ, `distractors` в задаче и `trap_hit` в истории ссылаются только на id из этого каталога. Иначе ловушки нельзя посчитать: «missed one case» и «forgot a case» стали бы разными ошибками (research/04).

Стартовый набор, дополню по опыту олимпиадных задач:

| id | Ловушка |
|---|---|
| `off_by_one` | ±1 при подсчёте промежутков, этажей, распилов |
| `missed_case` | пропустил вариант при переборе |
| `double_count` | посчитал один и тот же вариант дважды |
| `ignored_not` | не заметил «не» в условии |
| `answered_other_question` | ответил не на тот вопрос: спросили «сколько осталось», ответил «сколько взяли» |
| `stopped_early` | не довёл решение до конца, остановился на промежуточном результате |
| `wrong_operation` | не то действие: сложил вместо вычитания, умножил вместо деления |
| `reversed_relation` | перепутал направление сравнения: выше и ниже, раньше и позже, больше и меньше |
| `best_case_not_worst` | в задаче «наверняка» взял удачный случай вместо худшего (принцип Дирихле) |
| `trusted_statement` | поверил утверждению, не проверив, может ли говорящий лгать |
| `time_unit_mixup` | перепутал часы и минуты или посчитал в часе 100 минут |
| `number_from_text` | ответил числом из условия, ничего не посчитав |
| `wrong_parity` | ошибся в чётности: например, решил, что нечётное плюс нечётное — нечётное |
| `ignored_condition` | не учёл одно из условий: «разные», «ровно один раз», «с обоих концов» |

Последние восемь ловушек добавлены в T11: на сотни эталонов шести не хватило.

## 5. Роли и инструменты

```
Ученик ↔ чат AI-клиента (Claude, ChatGPT, …) — модель клиента пишет текст
                  │ вызовы инструментов MCP (5.8)
                  ▼
        MCP-сервер taskgen — наш код, без LLM
          get_student_profile · get_next_task · submit_task · submit_answer · get_progress
                  │
                  ▼
   профиль и рейтинги (5.6) · правило (5.7) · банк (5.5) · эталоны (4.3)
   проверки (6) · песочница для программы-решателя (5.3) → PostgreSQL
```

В прежнем замысле было четыре агента на Claude API: Методист, Генератор, Аналитик и Скептик. Теперь их роли распределены так (D42):

| Роль | Кто выполняет |
|---|---|
| Методист — что дать ученику | правило (5.7) даёт рекомендацию, модель клиента может изменить ТЗ с обоснованием |
| Генератор — задача по ТЗ | модель клиента, с эталонами и форматом от сервера |
| Аналитик — проверка ответа перебором | программа-решатель: пишет модель клиента, выполняет наша песочница (5.3) |
| Скептик — поиск дефектов | самопроверка модели по чек-листу (5.4) |
| Итоговая проверка качества | я, вручную (раздел 9) |

### 5.1 ТЗ на задачу (brief)

**Кто пишет:** сервер строит ТЗ по правилу (5.7) и показывает его модели как рекомендацию в `get_student_profile`, вместе с коридором по темам. Хочет модель другую тему или сложность — передаёт их в `get_next_task` вместе с причиной (`reason`): банк и эталоны подбираются уже под её выбор, в `rationale` попадают её причина и рекомендация правила, а в `requests.tutor_mode` пишется `llm`; без изменений — `rule`. Так сравниваются правило и модель (раздел 9). Сюжет, ловушки и ограничения модель уточняет в итоговом ТЗ, которое сдаёт вместе с задачей в `submit_task` (D43).

```json
{
  "rationale": "Two failures in a row: missed a case in enumeration, then didn't understand a clocks question. Give an easier, short enumeration task to rebuild confidence.",
  "pedagogical_goal": "motivate",
  "target_concept": "combinatorics.enumeration",
  "difficulty": 2,
  "setting": "space",
  "traps_to_use": ["missed_case", "double_count"],
  "constraints": ["question no longer than 3 sentences"],
  "excluded_skills": ["division_with_remainder", "fractions"],
  "profile_fields_used": ["consecutive_failures", "history", "cognitive_profile"]
}
```

`pedagogical_goal` принимает одно из трёх значений: `reinforce` (закрепить слабое место), `motivate` (дать задачу полегче для уверенности) или `new_topic` (перейти к новой теме).

`difficulty` берётся из коридора (5.6). Выйти за коридор можно (например, при `motivate` дать задачу полегче), но только с обоснованием в `rationale`. `traps_to_use` — id из `traps.json` (4.5).

`excluded_skills` переносится из профиля, чтобы в задаче не было этих навыков ни в условии, ни в ловушках. Их описания из `skills.json` модель получает в пакете `get_next_task`.

`profile_fields_used` — поля профиля, на которые опирался выбор. По ним видно, какие поля профиля реально работают, а какие лишние (см. раздел 9).

### 5.2 Задача

**Кто пишет:** модель клиента по ТЗ, трём эталонам и последним задачам ученика, чтобы не повторяться (модели склонны к однообразию, research/03). На повторной попытке — с причинами отказа прошлой. Задача сдаётся в `submit_task` в таком формате (`schemas/generator.json`), язык — отдельным параметром:

```json
{
  "core_idea": "Count unordered pairs among 4 objects: 4·3/2 = 6.",
  "design_thought_process": "Plot: spaceships docking. Trap 5: one pair missed. Trap 12: every pair counted twice.",
  "question": "…",
  "options": {"A": "4", "B": "5", "C": "6", "D": "8", "E": "12"},
  "correct_answer": "C",
  "solution": "…",
  "hint": "How many ships can the first ship dock with?",
  "distractors": {
    "A": {"trap": "…", "text": "…"},
    "B": {"trap": "missed_case", "text": "You missed one pair."},
    "D": {"trap": "…", "text": "…"},
    "E": {"trap": "double_count", "text": "You counted every pair twice."}
  }
}
```

- `core_idea` — математическое ядро задачи до сюжета: сначала идея и почему ответ такой, потом обёртка. Генерация от идей работает лучше (research/03).
- `solution` — пошаговое решение простым языком, как тренер объясняет ученику 1–4 класса. Сервер возвращает его после ответа ученика, модель по нему разбирает задачу.
- `hint` — один наводящий вопрос или первый шаг к решению. Ответ не раскрывает. Ученик видит его до ответа, если попросит.
- `distractors`: у каждого неверного варианта id ловушки (`trap`, из `traps.json`) и текст для ученика (`text`). По `trap` понимаем ошибку ученика (поле `trap_hit`), `text` ученик видит после неверного ответа.

### 5.3 Программа-решатель

Вместе с задачей модель сдаёт `solver_code` — короткую программу на Python, которая перебором проверяет каждый вариант A–E по условию задачи и печатает последней строкой JSON-список верных вариантов, например `["C"]`. Контракт: только стандартная библиотека, без ввода, детерминированно. Сервер выполняет её в песочнице (Docker без сети, с лимитами времени, памяти и CPU, `sandbox.py`) и требует ровно `[correct_answer]` (раздел 6).

У программы другие причины ошибок, чем у рассуждения LLM: она ловит арифметические и логические промахи в собственном ответе модели (research/05). **Ограничение:** программу пишет та же модель, что и задачу. Если модель неверно поняла собственное условие, программа подтвердит неверное прочтение. Неоднозначности в тексте ищет самопроверка (5.4), остальное ловит моя ручная проверка.

### 5.4 Самопроверка

Прежний Скептик. Перед сдачей модель проверяет задачу по чек-листу и сдаёт результат в `submit_task` как `self_check` (`schemas/skeptic.json`):

```json
{
  "issues": [
    {"type": "ambiguous", "severity": "blocking", "comment": "Unclear whether pairs A–B and B–A count as different."}
  ],
  "option_check": {
    "A": "wrong because …",
    "B": "wrong because …",
    "C": "correct",
    "D": "wrong because …",
    "E": "wrong because …"
  },
  "final_answer": "C"
}
```

- Возможные `type` в `issues`: `ambiguous`, `missing_data`, `multiple_correct`, `no_correct`, `too_hard_for_grade`, `needs_picture`, `factual_error`.
- `severity`: `blocking` (задачу отклоняем) или `minor` (задачу оставляем, замечание сохраняем для ручного разбора).
- `option_check` проверяет, что верен ровно один вариант.
- Если решить задачу нельзя, `final_answer` = `"UNSOLVABLE"`.
- Чек-лист явный: без прямого запроса модели распознают неоднозначность, но редко о ней сообщают (research/05). Модель проверяет:
  - не хватает ли условия;
  - можно ли прочитать условие двумя способами;
  - есть ли «не» и другие отрицания;
  - есть ли диапазоны и расплывчатые слова («несколько», «около»);
  - не противоречат ли условия друг другу;
  - не отвечает ли правильный вариант на другой вопрос.

Самопроверка слабее независимого Скептика: модель проверяет свой же текст. Поэтому сервер не полагается только на неё (раздел 6).

### 5.5 Банк задач

Все принятые задачи хранятся в таблице `tasks` (схема — в разделе 7). Перед генерацией сервер ищет в банке готовую задачу под ТЗ правила.

**Обязательные условия** (SQL `WHERE`):

- тема совпадает с ТЗ, а рейтинг задачи (5.6) попадает в коридор ученика по этой теме;
- уровень класса совпадает с классом ученика (1–2 или 3–4);
- язык задачи совпадает с языком чата;
- `tasks.excluded_skills @> <excluded_skills ученика>`: задача сгенерирована при тех же или более строгих запретах, значит запрещённых для ученика навыков в ней нет;
- задачи нет в `student_tasks` этого ученика: одну задачу ученик никогда не получает дважды, даже если тогда ошибся.

**Выбор лучшей** из подходящих (в коде): сначала совпадение `setting` с ТЗ, потом больше общих ловушек с `traps_to_use`. Не нашлось ни одной — модель пишет новую задачу.

Почему без pgvector: темы в каталоге дискретные, точных условий хватает, а поиск по смыслу может вернуть «похожую» тему вместо нужной. pgvector подключим, когда тексты ТЗ станут слишком разнообразными для точных условий.

Для задачи из банка в `requests` пишется источник `bank`, новых попыток и записей в датасетах не появляется. В историю ученика она попадает как обычно: `trap_hit` берётся из сохранённых `distractors`.

### 5.6 Рейтинги и коридор сложности (Эло + IRT)

Уровень ученика и сложность задач считаем кодом, а не LLM: LLM как модель ученика работают хуже классических методов (research/06). Модель — логистическая IRT (модель Раша) с поправкой на угадывание; параметры обновляются после каждого ответа по-эловски.

Вероятность, что ученик решит задачу:

P = 0,2 + 0,8 · σ(θ + δ_тема − β), где σ(x) = 1 / (1 + e^(−x))

- θ — общий уровень ученика;
- δ_тема — поправка на тему; у новой темы 0, то есть работает общий уровень (холодный старт);
- β — сложность задачи;
- 0,2 — угадывание: вариантов 5, штрафа нет.

Шахматная формула Эло E = 1 / (1 + 10^((R_задачи − R_ученика)/400)) — та же логистическая кривая в другом масштабе (R = 1500 + 174·θ). Для показа ученику рейтинги можно давать в этой шкале.

После ответа (S = 1 за верный ответ, S = 0 за неверный или «не понимаю»):

- θ += K_общ · (S − P)
- δ_тема += K_тема · (S − P)
- β −= K_задача · (S − P)

У каждого параметра свой K = K₀ / (1 + a·n): в начале рейтинг подстраивается быстро, потом стабильно.

- K₀ свой: `k0_student` для θ, `k0_topic` для δ, `k0_task` для β. Общий уровень двигается медленнее поправки по теме (0,2 против 0,4). Иначе на первых ответах уровень по теме θ + δ меняется почти на 0,8 · (S − P), и две ошибки подряд сдвигают его почти на целый уровень сложности.
- n тоже свой — число ответов до текущего: у ученика (`students.answers_count`), у темы (`student_topic_ratings.answers_count`), у задачи (`tasks.rating_count`).

Старт: θ = 0, δ = 0. Начальная β новой задачи — по её сложности внутри уровня класса: β = difficulty − 3, то есть 1 → −2, 2 → −1, 3 → 0, 4 → +1, 5 → +2.

`seed.py` прогоняет стартовую историю (4.1) через эти формулы и обновляет только θ и δ. Задач стартовой истории нет в банке, поэтому каждая считается новой задачей без ответов: её β берётся по сложности и нигде не сохраняется.

**Коридор сложности** — уровни сложности, при которых P попадает в [0,70; 0,85]: Math Garden держит успех около 0,75, «правило 85%» даёт верхнюю границу (research/06). Модель получает коридор по темам (5.1), банк ищет задачи с рейтингом внутри коридора (5.5).

Ширина коридора по шкале β — 0,96, а уровни сложности отстоят на 1, поэтому в коридор попадает не больше одного уровня, а иногда ни одного. **Рекомендуемая сложность** — уровень, у которого P ближе всего к середине коридора (0,775), с пометкой: в коридоре, сложнее коридора или легче коридора. Если уровень внутри коридора есть, выбирается именно он. Банк ищет по диапазону β коридора как есть: β задач непрерывна, и задачи с «уехавшей» β в нём найдутся.

Не добавляем:

- поправку на недавние результаты — на серию неудач реагирует выбор ТЗ через `consecutive_failures`;
- поправку на возраст — рейтинги задач ведутся внутри уровня класса.

Три K₀, a и границы коридора — в `config.yaml`.

### 5.7 Методист-правило (рекомендация и базовая линия)

Правило без LLM строит ТЗ в том же формате (5.1). Сервер отдаёт его модели как рекомендацию, а сравнение «правило против модели» проверяет первую гипотезу:

- цель и тема: после неудачи (`consecutive_failures` > 0) — `reinforce` по теме последней задачи; иначе `new_topic` — неосвоенная тема уровня класса ученика, которую он дольше всех не получал (сначала ни разу не выданные, по порядку каталога). Если освоены все темы уровня, выбор идёт среди всех;
- сложность — рекомендуемая по этой теме (5.6);
- сеттинг — по кругу из `interests`: берётся интерес с номером «число записей истории по модулю числа интересов»;
- ловушки — две: самые частые `trap_hit` ученика по теме, а если их меньше двух — добор самыми частыми ловушками эталонных задач этой темы и уровня класса (4.3).

Правило детерминировано: на одном профиле всегда получается одно и то же ТЗ (D40).

Если ТЗ, изменённые моделью, окажутся не лучше правила, это важный вывод прототипа (метрика «Адаптивность», раздел 9).

### 5.8 Инструменты MCP

| Инструмент | Что делает |
|---|---|
| `get_student_profile(student_id)` | профиль, последние 5 записей истории, по темам: уровень θ + δ, рейтинг в шахматной шкале, рекомендуемая сложность и пометка коридора; ТЗ-рекомендация правила (5.7) |
| `get_next_task(student_id, language, topic?, difficulty?, reason?)` | открывает запрос (`requests`); ТЗ по правилу или с темой и сложностью модели (5.1); подходящая задача из банка — выдаёт её ученику и отдаёт модели условие, варианты и подсказку, без ответа и решения. Иначе пакет для модели: ТЗ, коридор, описания темы, ловушек и запрещённых навыков, 3 эталона, последние задачи ученика, форматы ТЗ, задачи и самопроверки, лимиты читаемости и руководство с чек-листом |
| `submit_task(request_id, brief, task, solver_code, self_check, language)` | проверки раздела 6; принята — задача идёт в банк и выдаётся ученику; нет — все причины отказа для следующей попытки, до 3 попыток на запрос |
| `submit_answer(student_id, task_id, answer, hint_used)` | ответ — буква A–E или `?` («не понимаю»), один раз на выданную задачу; `correct`, `chosen_option`, `trap_hit`, `pace` (время считает сервер от выдачи до ответа), `consecutive_failures`, рейтинги θ, δ, β; возвращает, верен ли ответ, верный вариант, текст ловушки, решение и рейтинг по теме до и после |
| `get_progress(student_id)` | рейтинги по темам, освоенные темы, серия неудач, последние ответы |

Порядок работы для модели задают поле `instructions` сервера (файл `prompts/mcp_instructions.md`, на английском), руководство по написанию задачи (`prompts/task_writing.md`, приходит в пакете `get_next_task`) и описания инструментов. `prompt_version` — хэш файлов в `prompts/`, он пишется в каждую попытку: без него метрики разных версий инструкций смешиваются.

Логика инструментов живёт в `service.py` и тестируется без MCP, `mcp_server.py` — тонкий адаптер над Python SDK `mcp` (раздел 10).

## 6. Проверки и попытки

Задача **принимается**, если:

1. ТЗ, задача и самопроверка проходят свои JSON-схемы (`schemas/brief.json`, `generator.json`, `skeptic.json`); вариантов ровно 5 и все разные, в `distractors` ровно 4 ключа (все варианты, кроме верного), `hint` не пустой, id ловушек, тем и навыков — из каталогов (`filters.structure_errors`); тема и сложность ТЗ совпадают с запросом из `get_next_task`, а `excluded_skills` содержит все запреты ученика;
2. программа-решатель выполнилась в песочнице и вернула ровно `[correct_answer]`;
3. в самопроверке нет замечаний `blocking`, а её `final_answer` совпадает с `correct_answer`;
4. текст проходит фильтр читаемости: самое длинное предложение не длиннее порога для уровня класса — для любого языка; оценка Флеша-Кинкейда не выше класса ученика плюс запас — только для английского (`config.yaml`). LLM плохо держат уровень чтения младших (research/10);
5. нет близкого дубля среди задач банка и эталонов: триграммная похожесть `pg_trgm` ниже порога.

**Независимых проверяющих больше нет.** Задачу пишет и проверяет одна и та же модель клиента, а ошибки модели при проверке своего же текста коррелируют сильнее всего (research/05). Что остаётся: программа-решатель ломает часть этой корреляции, самопроверка по явному чек-листу ловит часть неоднозначностей, читаемость и дубли меряет код. **Главная защита от ложно принятых задач — моя ручная проверка** (раздел 9). Независимый проверяющий — после прототипа (раздел 11).

Коды причин отказа (`attempts.reason`), в порядке проверки:

| Код | Когда |
|---|---|
| `bad_structure` | не прошла схема или структурная проверка (условие 1) |
| `solver_error` | программа упала, не уложилась в лимит или напечатала не JSON-список букв |
| `self_check_blocking` | в самопроверке есть блокирующее замечание |
| `readability` | слишком длинное предложение или слишком высокий Флеш-Кинкейд |
| `near_duplicate` | близкий дубль в банке или среди эталонов |
| `solver_disagrees` | программа или самопроверка дали не тот ответ, что `correct_answer` |

Модель получает **все** невыполненные проверки сразу, чтобы исправить задачу за одну попытку; в `attempts.reason` пишется первая по порядку.

- Лимит — 3 попытки на запрос (`max_attempts`). После них запрос считается неудачным (`failed`), ученику ничего не выдаётся; модель сообщает об этом и может попросить новую задачу. Больше попыток не даём: если модель не справилась после двух прицельных исправлений, дальше она обычно перебирает те же нерабочие варианты, а отказ после 3 попыток сам по себе сигнал — по таблице `attempts` видно, на каких темах и ловушках модель спотыкается.
- Модель исправляет свою задачу как хочет: особого пути для ошибки в собственном ответе больше нет, это обычный отказ `solver_disagrees`.
- Замечания `minor` сохраняются вместе с задачей для ручного разбора.

## 7. Что хранится в БД

Всё хранится в PostgreSQL (Docker-контейнер, `docker-compose.yml`, схема в `db/schema.sql`). Файлов с результатами нет.

| Таблица | Что внутри | Зачем |
|---|---|---|
| `students` | Профиль ученика: класс, интересы, `cognitive_profile`, `mastered_topics`, `excluded_skills`, `consecutive_failures`, общий рейтинг θ | Вход для выбора задачи |
| `student_tasks` | Выданные ученику задачи и его ответы: `correct`, `chosen_option`, `trap_hit` (id ловушки), `feedback`, `hint_used`, `pace` | История (модели — последние 5 записей) и защита от повторной выдачи |
| `student_topic_ratings` | Поправки рейтинга ученика по темам (δ_тема) | Коридор сложности (5.6) |
| `tasks` | Банк: принятые задачи целиком — ТЗ, задача, программа-решатель и её результат, самопроверка, язык, число попыток, рейтинг сложности β | Повторное использование (см. 5.5). Отсюда же беру задачи для ручной проверки качества |
| `requests` | Один запрос задачи: ученик, чьё ТЗ (`rule` или `llm`), ТЗ, откуда задача (`bank`, `generated` или `failed`), число попыток, время | Метрики: доля из банка, попытки и время одной задачи |
| `attempts` | Каждая попытка, включая отклонённые: статус (`accepted` или `rejected`), код причины (раздел 6), задача, программа и её результат, самопроверка, версия инструкций, клиент MCP, время | Главный источник выводов по прототипу, в том числе на каких темах и ловушках задачи не проходят за 3 попытки |
| view `finetune_solver` | prompt: условие + варианты; completion: решение и ответ | Эталон для оценки решателей |
| view `finetune_generator` | prompt: ТЗ; completion: задача, прошедшая проверки | Эталон для оценки генераторов |

Датасеты — это view над `tasks`: в них попадают только принятые задачи, без дублей и без отдельной записи. **Дообучать на них не будем** (раздел 1); при необходимости view выгружается в JSONL. Отклонённые попытки остаются в `attempts`: это готовые примеры плохих задач.

Колонки `tokens` и `cost_usd` в `requests` и `attempts` остаются пустыми: своих вызовов LLM нет, а сколько потратил клиент, серверу не видно. Колонки `analyst` и `skeptic` хранят программу-решатель и самопроверку, `models` — `clientInfo` клиента MCP (название и версия), модель клиента серверу не сообщается.

```sql
CREATE TABLE students (
  student_id           text   PRIMARY KEY,
  grade                int    NOT NULL,
  interests            text[] NOT NULL,
  cognitive_profile    text[] NOT NULL,
  mastered_topics      text[] NOT NULL,
  excluded_skills      text[] NOT NULL,
  consecutive_failures int    NOT NULL DEFAULT 0,
  rating               real   NOT NULL DEFAULT 0,  -- общий уровень θ (5.6)
  answers_count        int    NOT NULL DEFAULT 0
);

CREATE TABLE student_topic_ratings (  -- поправки по темам δ_тема (5.6)
  student_id    text NOT NULL REFERENCES students,
  topic         text NOT NULL,           -- id темы из topics.json
  topic_offset  real NOT NULL DEFAULT 0,
  answers_count int  NOT NULL DEFAULT 0,
  PRIMARY KEY (student_id, topic)
);

CREATE TABLE tasks (                -- банк задач
  task_id         text PRIMARY KEY,
  created_at      timestamptz NOT NULL DEFAULT now(),
  topic           text   NOT NULL,  -- id темы из topics.json
  difficulty      int    NOT NULL,  -- сложность 1–5 (4.3)
  grade_level     text   NOT NULL,  -- '1-2' или '3-4'
  language        text   NOT NULL,  -- язык задачи, ISO 639-1: язык чата (1)
  setting         text,
  excluded_skills text[] NOT NULL,  -- запреты из ТЗ, под которое задача написана
  traps           text[] NOT NULL,
  brief           jsonb  NOT NULL,  -- итоговое ТЗ (5.1)
  task            jsonb  NOT NULL,  -- задача (5.2)
  analyst         jsonb  NOT NULL,  -- программа-решатель и её результат (5.3)
  skeptic         jsonb  NOT NULL,  -- самопроверка (5.4)
  attempt_count   int    NOT NULL,
  rating          real   NOT NULL,  -- сложность β (5.6), стартует от difficulty
  rating_count    int    NOT NULL DEFAULT 0
);

CREATE TABLE student_tasks (        -- выданные задачи и ответы = история ученика
  id            bigserial PRIMARY KEY,
  student_id    text NOT NULL REFERENCES students,
  task_id       text REFERENCES tasks,  -- NULL у записей из стартового профиля
  topic         text NOT NULL,
  difficulty    int  NOT NULL,
  issued_at     timestamptz NOT NULL DEFAULT now(),
  correct       boolean,                -- NULL: «не понял» или ещё не ответил
  chosen_option text,
  trap_hit      text,                   -- id ловушки из traps.json
  feedback      text,
  hint_used     boolean NOT NULL DEFAULT false,
  pace          text,                   -- 'fast', 'normal' или 'struggled'
  UNIQUE (student_id, task_id)
);

CREATE TABLE requests (             -- один запрос задачи для ученика
  request_id    bigserial PRIMARY KEY,
  created_at    timestamptz NOT NULL DEFAULT now(),
  student_id    text  NOT NULL REFERENCES students,
  tutor_mode    text  NOT NULL,         -- 'rule': ТЗ правила; 'llm': модель его изменила (5.1)
  brief         jsonb NOT NULL,         -- ТЗ из get_next_task; итоговое, с уточнениями модели, — в tasks.brief
  source        text  NOT NULL,         -- 'bank', 'generated' или 'failed'
  task_id       text  REFERENCES tasks, -- NULL, если 'failed'
  attempt_count int   NOT NULL DEFAULT 0,
  tokens        int,                    -- пусто: своих вызовов LLM нет (D42)
  cost_usd      numeric(10, 4),         -- пусто
  duration_ms   int                     -- от get_next_task до принятия задачи
);

CREATE TABLE attempts (             -- каждая попытка сдать задачу
  attempt_id  bigserial PRIMARY KEY,
  request_id  bigint NOT NULL REFERENCES requests,
  attempt_no  int    NOT NULL,        -- 1–3
  status      text   NOT NULL,        -- 'accepted' или 'rejected'
  reason      text,                   -- код причины отказа (раздел 6)
  generator   jsonb,                  -- задача
  analyst     jsonb,                  -- программа-решатель
  skeptic     jsonb,                  -- самопроверка
  solver_result  jsonb,               -- что вернула программа в песочнице
  prompt_version text NOT NULL,       -- хэш инструкций сервера (5.8)
  models      jsonb,                  -- clientInfo клиента MCP
  tokens      int,                    -- пусто
  cost_usd    numeric(10, 4),         -- пусто
  duration_ms int
);

CREATE VIEW finetune_solver AS      -- датасет решателя
  SELECT task_id,
         jsonb_build_object('question', task -> 'question', 'options', task -> 'options') AS prompt,
         jsonb_build_object('solution', task -> 'solution', 'answer', task -> 'correct_answer') AS completion
  FROM tasks;

CREATE VIEW finetune_generator AS   -- датасет генератора
  SELECT task_id, brief AS prompt, task AS completion
  FROM tasks;
```

Колонка `tasks.language` и новый `finetune_solver` появятся в `db/schema.sql` в T20.

## 8. Модель клиента вместо своего LLM

- **Текст пишет модель AI-клиента** в рамках подписки пользователя. У нас нет ни ключей API, ни счёта за токены; платим только за свою инфраструктуру (D42).
- **Почему генерация идёт в разговоре.** В MCP есть sampling — механизм, при котором сервер сам просит модель клиента что-то сгенерировать. Но claude.ai, Claude Desktop и Claude Code его пока не поддерживают. Поэтому сервер отдаёт модели требования, эталоны и формат, модель пишет задачу в разговоре и сдаёт её инструментом `submit_task`.
- **Клиенты.** Прототип — Claude Code локально: сервер запускается через stdio по `.mcp.json` в корне репозитория, без хостинга и OAuth. Тот же код потом открывается по Streamable HTTP для claude.ai и Claude Desktop (свой коннектор, OAuth) и для ChatGPT (режим разработчика, публичный HTTPS) — раздел 11.
- **Лимиты клиентов:** у claude.ai и Desktop — 4 минуты на вызов инструмента и около 150 тысяч символов на ответ; у Claude Code — 25 тысяч токенов на ответ по умолчанию. Пакет `get_next_task` держим в пределах нескольких тысяч токенов.
- **Модель заранее неизвестна.** Какая модель у пользователя, серверу не сообщается; пишем `clientInfo` клиента и смотрим метрики по клиентам (раздел 9). Качество задач зависит от модели клиента — это часть гипотезы.
- **Известное ограничение.** Задачу пишет и проверяет одна модель (раздел 6). Независимый проверяющий — после прототипа (раздел 11).

```yaml
max_attempts: 3       # попыток submit_task на один запрос (6)
pace:                 # пороги для тега pace, время от выдачи задачи до ответа
  fast_below_sec: 60
  struggled_above_sec: 180
rating:               # Эло + IRT (5.6), значения примерные; у θ, δ и β свой K = k0 / (1 + decay·n)
  k0_student: 0.2
  k0_topic: 0.4
  k0_task: 0.4
  decay: 0.05
  corridor: [0.70, 0.85]
sandbox:              # Docker без сети (5.3), образ закреплён по дайджесту
  image: python:3.12.14-slim-trixie@sha256:78387bc3881b8273120a12ebe6c1ab22b018ccc2c9adf565ae1ac9b536e184ea
  timeout_sec: 10
  memory_mb: 256
  cpus: 1
readability:          # по тексту условия (question)
  max_grade_margin: 3 # Флеш-Кинкейд не выше класса ученика + 3, только для английского
  max_sentence_words: { "1-2": 20, "3-4": 25 }  # самое длинное предложение, по уровню класса
near_duplicate:
  max_similarity: 0.6 # pg_trgm
```

### Стоимость

- **LLM:** $0 для нас. Живые прогоны в Claude Code расходуют лимиты подписки автора, а у учеников — их собственные.
- **Инфраструктура:** в прототипе всё локально (PostgreSQL и песочница в Docker). Хостинг — после прототипа.

## 9. Как понять, что прототип удался

| Метрика | Как считаем | Цель |
|---|---|---|
| Принято с 1-й попытки | `requests`: доля `generated` с `attempt_count = 1` среди запросов с генерацией | > 50% |
| Принято за ≤ 3 попытки | `requests`: `generated` / (`generated` + `failed`) | > 80% |
| Качество по ручной проверке | Я (не LLM) проверяю 20–30 принятых задач (см. «Кто проверяет качество» ниже): решаема, однозначна, похожа на хорошую олимпиадную задачу, подходит по возрасту, подсказка не выдаёт ответ, ловушки и разбор понятны ребёнку, дистракторы правдоподобны, нет стереотипов в сюжете и персонажах | > 90% |
| **Ложно принятые** | Прошли проверки сервера, но при ручной проверке оказались математически плохими: неверный ответ, неоднозначное условие, нет решения или верны несколько вариантов. Главная метрика проверок | 0 (не больше 2%) |
| Программа не согласилась с моделью | Доля попыток с `solver_disagrees`: насколько часто модель ошибается в собственном ответе | без цели, наблюдаем |
| Самопроверка нашла дефект | Доля попыток с `self_check_blocking` и замечаний `minor` у принятых задач | без цели, наблюдаем |
| Доля задач из банка | `requests`: доля `source = 'bank'` | без цели, наблюдаем |
| Какие поля профиля работают | Частота полей в `profile_fields_used` из `requests.brief` | без цели, наблюдаем |
| Адаптивность | Сравнение ТЗ правила и ТЗ, изменённых моделью (`requests.tutor_mode`): у кого доля верных ответов чаще попадает в коридор 70–85%, и чьи ТЗ лучше по моей слепой оценке пар (не знаю, какое ТЗ от кого). Плюс: после ошибок модель меняет цель, а свежий `trap_hit` виден в следующем ТЗ | модель лучше правила |
| Разнообразие | 20 задач на одну тему не повторяют друг друга по сюжету и идее: автоматически по триграммной похожести (`pg_trgm`) плюс моя ручная проверка | > 80% уникальных сюжетов |
| Время одной принятой задачи | Секунды от `get_next_task` до принятия с учётом попыток, из `requests.duration_ms`. Только `generated`, без задач из банка | < 90 с |
| Метрики по клиентам | Всё выше в разрезе `attempts.models` (клиент MCP) | без цели, наблюдаем |

Стоимость LLM для нас — ноль по построению, поэтому отдельной метрики цены нет.

**Сценарии для оценки.** Фиксированные сценарии живых прогонов на 5 профилях (`data/eval/`): попросить задачу, решить, ошибиться, «не понимаю», посмотреть прогресс. Каждая новая версия инструкций прогоняется на них, а метрики сравниваются по `attempts.prompt_version`.

### Кто проверяет качество

Качество проверяю я, автор прототипа, вручную (не LLM): у меня большой опыт решения олимпиадных задач и тренировки ребёнка на них с хорошим результатом. Внешние эксперты на этапе прототипа не нужны.

Я просматриваю 20–30 принятых задач по критериям из таблицы выше: решаема, однозначна, похожа на хорошую олимпиадную задачу, подходит по возрасту, подсказка не выдаёт ответ, ловушки и разбор понятны ребёнку, дистракторы правдоподобны, нет стереотипов.

## 11. После прототипа

1. **Удалённый режим.** Тот же сервер по Streamable HTTP за HTTPS (хостинг или туннель): свой коннектор в claude.ai и Claude Desktop (все тарифы), приложение в режиме разработчика ChatGPT. Авторизация через OAuth: пользователь клиента → ученик MathTrail, без передачи ключей.
2. **MCP Apps.** Интерактивная карточка задачи прямо в чате: условие, варианты, кнопка ответа. Ответ и разбор не видны ребёнку до ответа, а ответ сразу уходит в `submit_answer`.
3. **Независимая проверка.** Второй проверяющий, не та модель, что писала задачу: sampling, когда клиенты его поддержат, другая модель клиента или своя локальная модель.
4. **Как роли прототипа ложатся на сервисы MathTrail:**

| В прототипе | В MathTrail |
|---|---|
| MCP-сервер (`mcp_server.py`) | один MathTrail MCP для Claude, ChatGPT и других клиентов |
| Профиль, история и рейтинги (`students`, `student_tasks`, `student_topic_ratings`) | `profile-api` (+ pgvector). Там автоматически считаются рейтинги, `pace`, `consecutive_failures`, `mastered_topics` и сводка истории, а `cognitive_profile` обновляется по `trap_hit` |
| Банк задач и журналы (`tasks`, `requests`, `attempts`) | БД задач в целевой системе |
| Методист-правило и выбор ТЗ | `mentor-api` |
| Проверки задачи и песочница | `task-api` или `solution-validator` **[решить]**: он пока задуман для проверки решений ученика, а не задач |
| Ответ ученика и обновление профиля | `solution-validator` + `profile-api` |

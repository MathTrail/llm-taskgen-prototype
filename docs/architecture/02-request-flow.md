# 02. Поток одного запроса и цикл `--answer`

> Задача T02 из [RUN.md](../../RUN.md). Источник — [SPEC.md](../../SPEC.md), разделы 3, 5, 6. Компоненты — из [01-context.md](01-context.md).
>
> **Устарело после перехода на MCP (D42).** Диаграммы ниже описывают консольный запуск и цикл `--answer` с агентами на Claude API. Теперь запрос идёт из чата AI-клиента через инструменты MCP — порядок шагов в SPEC 3 и 5.8. Замечания этого файла закрыты решением D42: ТЗ в консоли больше не печатается (02-1), `pace` считает сервер по полному времени от выдачи до ответа, с подсказкой (02-2).

Здесь показано, в каком порядке вызываются компоненты и в какой момент что пишется в БД. Агенты ходят в Claude через `llm.py` — на схемах это не показано, чтобы не загромождать.

## 1. Одиночный запуск

`python -m taskgen.main --student masha [--fresh] [--tutor rule]`

```mermaid
sequenceDiagram
    autonumber
    actor Me as Я
    participant M as main.py
    participant DB as db.py / PostgreSQL
    participant R as rating.py
    participant T as Методист
    participant G as Генератор
    participant A as Аналитик
    participant S as Скептик
    participant X as sandbox.py
    participant C as проверки

    Me->>M: main.py --student masha
    M->>DB: профиль, последние 5 записей истории, рейтинги
    DB-->>M: профиль и рейтинги
    M->>R: коридор сложности по темам
    R-->>M: рейтинг и рекомендуемая сложность по каждой теме

    alt режим llm (по умолчанию)
        M->>T: профиль, коридор, каталоги тем и ловушек
        T-->>M: ТЗ (brief)
    else режим rule
        M->>M: tutor_rule.py выдаёт ТЗ того же формата
    end
    M-->>Me: ТЗ в консоль
    M->>DB: INSERT requests (tutor_mode, brief)

    opt без --fresh
        M->>DB: кандидаты из банка: тема, рейтинг в коридоре, уровень класса, запреты, ученик не получал
        DB-->>M: кандидаты
        M->>M: выбрать лучшую: совпадение setting, общие ловушки
    end

    alt в банке нашлась задача
        M->>DB: UPDATE requests: source = bank
    else генерация
        loop попытка 1, 2, 3
            M->>G: ТЗ, 3 эталона, случайное «зерно», причина прошлого отказа
            G-->>M: задача с задуманным ответом X
            par параллельно
                M->>A: только условие и варианты
                A-->>M: ответ Y, разбор, solver_code
            and
                M->>S: только условие и варианты
                S-->>M: ответ Z, issues, option_check
            end
            M->>X: solver_code
            X-->>M: список верных вариантов W или ошибка
            M->>C: структура, читаемость, близкие дубли
            C->>DB: similarity через pg_trgm (банк и эталоны)
            C-->>M: ok или код причины
            M->>DB: INSERT attempts (status, reason, ответы агентов, solver_result, prompt_version)
            break все 6 условий приёма выполнены
                M->>DB: INSERT tasks (задача с рейтингом по сложности)
            end
            Note over M,G: отказ: код причины уходит Генератору в следующую попытку.<br/>generator_answer_error: следующая попытка исправляет ту же задачу,<br/>верификаторы и программа повторно не вызываются
        end
        M->>DB: UPDATE requests: source = generated или failed, attempt_count, токены, стоимость, время
    end

    alt задача есть
        M->>DB: INSERT student_tasks (выдача ученику)
        M-->>Me: задача, варианты, ответ, разбор Аналитика, сводка
    else failed
        M-->>Me: «задача не получилась», выход с ошибкой
    end
```

## 2. Цикл `--answer`

`python -m taskgen.main --student masha --answer`

Шаг «запрос задачи» — это весь поток из схемы 1, от чтения профиля до записи в `student_tasks`.

```mermaid
sequenceDiagram
    autonumber
    actor Me as Я (как ученик)
    participant M as main.py
    participant F as запрос задачи (схема 1)
    participant DB as db.py / PostgreSQL
    participant R as rating.py

    Me->>M: main.py --student masha --answer
    loop до ввода exit
        M->>F: запросить задачу (передать неудавшееся ТЗ, если было)
        alt задача не получилась за 3 попытки
            F-->>M: failed
            M-->>Me: «задача не получилась»
            Note over M: в следующей итерации Методист получает неудавшееся ТЗ,<br/>чтобы не выбрать то же самое
        else задача есть
            F-->>M: задача (уже записана в student_tasks)
            M-->>Me: условие и варианты, запуск таймера
            opt ввод H
                Me->>M: H
                M-->>Me: подсказка (hint), hint_used = true
            end
            break ввод exit
                M-->>Me: конец сессии
            end
            Me->>M: A–E или ?
            M-->>Me: разбор: текст ловушки distractors[буква].text, если неверно, затем решение Аналитика
            M->>DB: UPDATE student_tasks: correct, chosen_option, trap_hit, feedback, hint_used, pace
            M->>R: S = 1 за верный, 0 за неверный или ?
            R-->>M: новые θ, δ_тема, β
            M->>DB: рейтинги ученика и задачи, consecutive_failures
            Note over M,DB: всё пишется сразу: следующий запуск продолжит с того же места
        end
    end
```

## Сверка со SPEC

**SPEC 3 — одиночный запуск:**

| Шаг SPEC | Где на схеме 1 |
|---|---|
| 1. Профиль и рейтинги из БД, коридор | запросы к `db.py` и `rating.py` в начале |
| 2. Методист выдаёт ТЗ, печать в консоль | блок `alt` llm / rule, «ТЗ в консоль» |
| 3. Поиск в банке | блок `opt без --fresh` и ветка «в банке нашлась задача» |
| 4. Генератор → Аналитик + Скептик → программа, до 3 попыток | `loop` с блоком `par` и вызовом `sandbox.py` |
| 5. Выдача в `student_tasks` | INSERT `student_tasks` в конце |
| 6. Вывод в консоль со сводкой | последнее сообщение Я |
| 7. Запрос и попытки в БД | INSERT/UPDATE `requests`, INSERT `attempts` |
| Флаг `--fresh` | блок `opt без --fresh` пропускается |

**SPEC 3 — цикл `--answer`:**

| Шаг SPEC | Где на схеме 2 |
|---|---|
| 1. Профиль и 5 записей истории | внутри «запрос задачи» (схема 1) |
| 2. Задача, запись в `student_tasks` | ответ «задача есть» |
| 3. Ввод `A`–`E`, `?`, `H`, `exit` | блоки `opt ввод H`, `break ввод exit`, сообщение «A–E или ?» |
| 4. Разбор | сообщение «разбор» |
| 5. Ответ в `student_tasks` | UPDATE `student_tasks` |
| 6. `consecutive_failures` и рейтинги | вызов `rating.py` и запись рейтингов |
| 7. Методисту последние 5 записей | внутри «запрос задачи» |
| 8. Следующая итерация | внешний `loop` |
| Неудача за 3 попытки | ветка «задача не получилась» |

**SPEC 6 — условия приёма:**

| Условие | Где на схеме 1 |
|---|---|
| 1. JSON по схеме, 5 вариантов, 4 дистрактора, `hint` | вызов «проверки» (структура) |
| 2. X == Y == Z | ответы Генератора, Аналитика и Скептика |
| 3. Программа вернула ровно `[X]` | вызов `sandbox.py` |
| 4. Нет блокирующих issues | ответ Скептика |
| 5. Читаемость | вызов «проверки» |
| 6. Нет близкого дубля | «проверки» → `pg_trgm` |
| Аналитик и Скептик параллельно | блок `par` |
| Ретрай с причиной, `generator_answer_error` | заметка внутри `loop` |

## Замечания к SPEC

Замечания из [01-context.md](01-context.md) остаются в силе. Новые:

1. **Когда показывать ТЗ в режиме `--answer`.** SPEC 3 требует печатать ТЗ Методиста в консоль, но в `--answer` я играю ученика, и ТЗ раскрывает тему и ловушки заранее. Предложение: в `--answer` ТЗ не показывать, а показывать по флагу `--show-brief`.
2. **`pace` при подсказке.** Таймер идёт от показа задачи до ответа, то есть с подсказкой время больше. В SPEC не сказано, считать ли время подсказки. Предложение: считать полное время. Подсказка и так видна в `hint_used`.

# RUN.md — план реализации прототипа

> Источник истины — [SPEC.md](SPEC.md). Этот файл задаёт порядок работы: маленькие задачи, которые запускаются по одной. После каждой задачи я проверяю результат и только потом запускаю следующую.

## Как пользоваться

Задача запускается одной фразой в новой сессии:

```
Выполни задачу T07 из RUN.md
```

**Правила для исполнителя (Claude):**

1. Делать только указанную задачу. Файлы других задач не трогать, кроме того, что задача прямо требует.
2. Перед началом прочитать `SPEC.md` и разделы, указанные в задаче. Если задача противоречит SPEC или чего-то не хватает — остановиться и спросить, а не додумывать.
3. Задачи с вызовами Claude API: до первого вызова назвать ожидаемую стоимость и дождаться подтверждения.
4. Не коммитить. Коммит делаю я после проверки.
5. В конце — короткий отчёт: что сделано, какие файлы, как проверить (команды), что осталось открытым.
6. Статус в таблице не менять — его отмечаю я после проверки.
7. Код, промпты и данные — на английском; документы и отчёты — на русском.

**Статусы:** `[ ]` — не начата, `[x]` — проверена мной.

**Нужно до фаз 1–3:** Docker, `uv`, ключ API Anthropic в `.env` (понадобится с T18).

### T02. Поток одного запроса и цикла `--answer`

- **Цель:** увидеть порядок вызовов и в какой момент что пишется в БД.
- **Сделать:** `docs/architecture/02-request-flow.md`, две `sequenceDiagram`:
  1. **Одиночный запуск:** профиль и рейтинги из БД → коридор → Методист → поиск в банке → (не нашлась) Генератор → Аналитик и Скептик параллельно → песочница → фильтры → решение → запись в `requests`, `attempts`, `tasks`, `student_tasks`; ретрай с причиной отказа.
  2. **Цикл `--answer`:** ввод ответа, подсказка, разбор, запись ответа, обновление рейтингов, следующая итерация; что происходит, если задача не получилась за 3 попытки.
- **Как проверить:** каждый шаг из SPEC 3 и 6 находится на диаграмме; видно, что Аналитик и Скептик идут параллельно.
- **SPEC:** 3, 5, 6.

- **SPEC:** 5.5, 5.6, 7.

### T04. Автомат состояний попытки

- **Цель:** увидеть все исходы попытки и что происходит после каждого.
- **Сделать:** `docs/architecture/04-attempt-states.md`:

  - таблица: код причины → что передаётся Генератору в следующую попытку.
- **Как проверить:** каждый код причины из SPEC 6 есть на схеме; лимит 3 попытки соблюдён; путь исправления `generator_answer_error` не вызывает верификаторов повторно.
- **SPEC:** 6, 7.

### T05. Рейтинги на числовом примере

- **Цель:** проверить математику Эло + IRT на бумаге до кода.
- **Сделать:** `docs/architecture/05-ratings.md`:
  - схема потока: ответ → P → обновление θ, δ, β → новый коридор;
  - числовой пример: новый ученик (θ = 0), одна тема, три ответа подряд — верно, неверно, «?» — на задачах 3, 4 и 4 балла; K₀ = 0.4, decay = 0.05. Все промежуточные P, K, θ, δ, β и коридор после каждого шага. Числа посчитать скриптом, а не в уме;
  - таблица «баллы → β → P для θ = −1, 0, +1».
- **Как проверить:** первый шаг могу пересчитать вручную; после ошибки коридор сдвигается к более лёгким задачам.
- **Результат пригодится:** числа станут тестовыми данными для T13.
- **SPEC:** 5.6.
